# 界序 INTERFACE 知识域分类提案（内部代号 UI Motion Lab）

- 日期：2026-11-08
- 时间盒：21:09–22:00（Asia/Shanghai）
- 性质：调研与提案，未改动项目既有文档、未写代码、未安装依赖
- 结论状态：推荐方案已成型，部分平台来源标注「待核」

---

## 0. 一页结论

**4 个域不够，建议扩为 7 个域。**

| 决策 | 内容 |
|---|---|
| 保留 | 风格 Style、动效 Motion、交互反馈 Feedback、组件 Components |
| 改造 | Feedback 扩为「反馈与状态 Feedback & State」，纳入 loading / empty / error / offline / 权限请求 |
| 新增 | 布局与结构 Layout & Structure、内容与文案 Content & Language、可及性与适配 Accessibility & Adaptation |
| 不新增 | 主题 Theme（归风格域二级）、平台规范（降为跨域 facet）、性能体感（归反馈/加载 + 标签）、权限与通知（归反馈/组件）、深浅主题（归主题标签） |
| 风格组织 | 按成因分 4 家族：材质系、流派系、平台系、结构系；主归属唯一，次归属最多 2 个 |
| 关系表达 | 父子用 `parent_id`（演进/派生），近亲同族用 `kin_group`，别名用 `aliases[]`；不做平铺 |
| 清单规模 | 79 条：风格 19、控件 33、主题 6、动效 10、反馈 11 |

一句话：**按「做 App 时要依次回答的问题」分域，不按组件菜单分域；跨域维度只做标签，不抢主域。**

## 1. 方法与判定规则

### 1.1 来源分层

| 层级 | 来源 | 用途 |
|---|---|---|
| A 一手规范 | Apple HIG、Material Design 3、Fluent 2、W3C WCAG 2.2、NN/g | 定域、定边界、定验收 |
| B 组件库官方分类 | shadcn/ui、Radix、Fluent UI React、Ant Design | 校验二级类目能否当筛选器 |
| C 行业词表 | World of Vibe Coding、vibecoding.rest、CodingWithVibe | 校验真实用语，不直接当规范 |
| D 趋势/营销内容 | 博客、风格词典、落地页 | 仅用于溯源命名，明显营销化的剔除 |

### 1.2 归域四问

每条知识入库前依次回答：

1. **它回答的是「看起来怎样」「怎么动」「什么触发什么回应」「由哪些零件组成」「怎么排」「说什么」「谁能用」中的哪一个？** 只选一个主问题。
2. **删掉它，哪一类知识会消失？** 消失的那一类就是主域；其他受影响的是关联。
3. **它是页面级、组件级还是参数级？** 页面级优先进结构，组件级进组件，参数级进风格/主题。
4. **它能不能直接当筛选器？** 不能当筛选器的，降为标签，不升二级类目。

### 1.3 主域 / 次域规则

- 每条案例只有一个主域，主域决定左栏归属。
- 次域最多 2 个，只用于「相关推荐」和交叉检索，不参与主筛选。
- 同一名称在不同域出现时，必须换词或加限定语。例如「空状态」：组件域条目叫「空状态组件（外观）」，反馈域条目叫「空状态触发（时机与下一步）」。
- 平台（iOS / Android / Web / 桌面 / 鸿蒙）是 **facet 标签**，不是域。理由是：平台规范没有独立于四域之外的内容，它只是给同一知识加「适用平台」维度；独立成域会把同一案例复制 5 份。

## 2. 推荐方案 A：按设计要素 / 职责分域

### 2.1 一级域总表

| # | 一级域 | 回答的问题 | 二级类目（可直接做筛选器） | 收什么 | 不收什么 | 与相邻域的分界 |
|---|---|---|---|---|---|---|
| 1 | 风格 Style | 看起来是什么气质、表面是什么做的、遵循谁家的规矩 | 材质系、流派系、平台系、结构系、色彩系统、字体与字阶、图标与插画、形状与层级、主题（明暗/品牌/跟随系统） | 视觉语言、可复用视觉 token、风格家族、主题换皮 | 组件结构、交互行为、信息架构、文案 | 风格只给 token 与表皮；组件给解剖；结构给排布 |
| 2 | 布局与结构 Layout & Structure | 信息怎么分组、页面怎么排、屏幕怎么变 | 信息架构、导航模型、页面骨架、栅格与间距、响应式与断点、密度与安全区、多端布局 | 页面级组织、层级、重排、导航模型选择 | 单个组件内部结构、视觉风格、触发逻辑 | 结构管「导航模型与页面层级」，组件管「导航控件的形态」；结构管重排，适配管能力差异 |
| 3 | 动效 Motion | 状态之间怎么过渡 | 转场、微交互、手势动效、缓动与时长、弹簧与物理、编排、共享元素、减弱动效 | 时间过程、运动规律、过渡编排 | 触发条件、结果反馈、静态样式 | 反馈决定「要不要动、回应什么」，动效决定「怎么动」 |
| 4 | 反馈与状态 Feedback & State | 什么触发什么回应、系统现在处于什么状态 | 交互状态、校验与错误、操作结果、通知提醒、确认与撤销、加载/空/错/离线、权限请求 | 事件到回应、状态覆盖、系统状态语义 | 过渡曲线、控件外观、文案措辞 | 反馈管机制与时机，动效管过程，组件管外观，内容管措辞 |
| 5 | 组件 Components | 有哪些零件、长什么样、在哪 | 基础控件、复合模式 | 控件与复合模式的形态、尺寸、变体、内部布局、状态外观 | 页面级排布、触发逻辑、状态间过渡 | 组件管「零件」，结构管「页面」，反馈管「行为」 |
| 6 | 内容与文案 Content & Language | 说什么、用什么词、怎么随语言变 | 微文案、错误与空状态文案、引导与教学、术语与语气、国际化与本地化 | 语言层、信息表达、翻译与 RTL | 排版视觉、交互机制 | 风格管字体与排版，内容管措辞；反馈管机制，内容管句子 |
| 7 | 可及性与适配 Accessibility & Adaptation | 不同能力、设备、输入方式的人能不能用 | 视觉可及性、键盘与焦点、辅助技术、运动与听觉、目标尺寸、输入方式与平台能力 | 可用性验收门槛、适配规则、降级策略 | 具体组件实现、整体视觉风格 | 组件管「可及性契约」，本域管「验收与降级」；结构管重排，本域管输入方式与能力差异 |

### 2.2 新增 / 不新增判定表

| 候选 | 判定 | 理由 | 去处 |
|---|---|---|---|
| 布局与结构 | 新增一级域 | 现有 4 域没有任何一个回答「信息怎么分组、页面怎么排、屏幕怎么变」；这是做 App 的第一批问题 | 一级域 2 |
| 内容与文案 | 新增一级域 | Apple HIG 有 Writing、Right to left；M3 有 Content design；NN/g 有微文案与内容策略。现有 4 域装不下「说什么」 | 一级域 6 |
| 可及性与适配 | 新增一级域 | WCAG 2.2 有独立原则与验收标准；它是发布门槛，不是某个组件的标签。案例可单独成条（焦点顺序、跳转链接、减弱动效） | 一级域 7 |
| 主题 Theme | 不独立成域，归风格域二级 | 它答「同一套界面怎么换皮」，本质是 token 维度：深浅、品牌色、强调色、跟随系统、继承覆盖。独立成域会与风格的色彩/字体/形状大量重复 | 风格域二级「主题」+ 跨域标签 `theme` |
| 平台规范 | 不独立成域 | 平台只决定「适用」，不产生新知识；独立会把同一案例复制多份 | facet 标签 `platform` |
| 性能体感 | 不独立成域 | 独立内容太少，主要是 loading / skeleton / optimistic UI / 防抖节流；其知识主体在反馈与动效 | 反馈域「加载与等待」+ 标签 `perf` |
| 权限与通知 | 不独立成域 | 权限请求是反馈时机问题，通知是组件+反馈问题；没有独立的视觉语言 | 反馈域「权限请求/通知」+ 组件域「Banner/Toast」 |
| 深浅主题 | 不独立成域 | 是主题的子集，不是并列项 | 主题二级 / 标签 `dark-mode` |
| 表单校验 | 不独立成域 | 是「触发什么回应」的典型，跨组件、反馈、内容三域 | 主域反馈；次域组件、内容 |
| 信任、隐私、商业化 | 不新增 | 属于产品/业务知识，不是 UI 设计知识库的核心；只保留与界面相关的权限、同意、付费墙标签 | 标签 |
| AI / Generative UI | 暂不新增 | 词表命中，但目前只有概念，没有稳定的形态参数与验收标准；先做跨域标签 | 标签 `generative-ui`，观察后再评估 |

### 2.3 备选方案对比

| 方案 | 划分依据 | 优点 | 缺点 | 适用 | 结论 |
|---|---|---|---|---|---|
| A 按设计要素/职责 | 视觉、结构、运动、行为、零件、语言、可及性 | 与「做 App 依次回答的问题」同构；筛选稳定；去重成本低；跨平台 | 边界需要纪律，否则风格会吸走结构、反馈会吸走动效 | 主方案 | **推荐** |
| B 按用户旅程 | 首次进入→理解→操作→等待→出错→离开→回访 | 贴近案例叙事，用户容易按场景找 | 同一案例跨多个阶段，主域不稳定；组件参考会被打散；不适合当左栏长期模型 | 作为二级 facet `journey` | 不采用为主方案 |
| C 按平台规范 | Apple / Material / Fluent / Web / 鸿蒙 | 平台合规检索最快；团队分工清晰 | 同一知识复制多份；跨平台原则被淹没；新平台不断出现，模型不稳定 | 作为 facet `platform` | 不采用为主方案 |
| D 按质量维度 | 可用、可及、性能、一致、国际化 | 适合验收清单与 QA | 不适合创作期浏览；会把「怎么做」拆成「哪里不合格」 | 作为标签与验收视图 | 不采用为主方案 |

**主题在四个方案中的位置：**

- A：风格域二级「主题」，与色彩、字体、形状并列，最稳。
- B：主题被拆到「首次进入/回访」等阶段，检索会碎。
- C：每个平台一套主题，重复严重。
- D：主题被归入「适配」，会丢掉品牌表达。
- 结论：**A + 风格域二级「主题」+ 跨域标签 `theme`**。

## 3. 与现有 4 域的差异清单

| 现有域 | 变化 | 具体改动 | 影响 |
|---|---|---|---|
| 风格 Style | 保留并结构化 | 二级从平铺名单改为「4 家族 + 5 视觉基元 + 主题」；新增父子/同族/别名关系；新增预览参数集 | 左栏风格不再是一长串名词；支持「做玻璃感」和「苹果味」两条检索路径 |
| 动效 Motion | 保留并细化 | 二级固定为转场、微交互、手势、缓动、弹簧、编排、共享元素、减弱动效 | 动效条目可按意图筛选，不再只按「动效」一个桶 |
| 交互反馈 Feedback | 扩名与扩域 | 显示名改为「反馈与状态」；纳入 loading / empty / error / offline / 权限请求；新增校验与通知二级 | 解决「状态覆盖」无处可放的问题；与组件域的空状态条目用限定语区分 |
| 组件 Components | 保留两层 | 二级仍只保留「基础控件」「复合模式」；解剖、尺寸、变体、状态外观、可及性契约降为标签 | 不破坏既定的两层模型；筛选器保持简单 |
| 新增 布局与结构 | 新域 | 信息架构、导航模型、页面骨架、栅格、响应式、密度、多端 | 承接原先散落在组件里的导航条/侧栏的「模型选择」问题 |
| 新增 内容与文案 | 新域 | 微文案、错误/空状态文案、引导、术语与语气、国际化 | 承接按钮文案、错误句、空状态句、翻译与 RTL |
| 新增 可及性与适配 | 新域 | 视觉、键盘焦点、辅助技术、运动听觉、目标尺寸、输入方式 | 承接 WCAG 验收与平台能力差异；组件域保留「契约」标签 |

## 4. 风格域：按成因分家族

### 4.1 四个家族的定义

| 家族 | 回答的问题 | 判定标志 | 典型条目 |
|---|---|---|---|
| 材质系 | 表面是什么做的 | 主要由背景透明度、模糊、纹理、内外阴影、边缘高光决定 | 玻璃拟态、液态玻璃、新拟态、拟物化、黏土拟态 |
| 流派系 | 视觉语言站哪一边 | 主要由色彩饱和度、字体、形状纪律、装饰程度决定 | 扁平、极简、粗野主义、新粗野主义、编辑式、触感设计、赛博朋克 |
| 平台系 | 遵循哪家的规矩 | 绑定某平台，且同时规定组件、动效、无障碍与布局 | Material 3、Fluent 2、Apple HIG、HarmonyOS Design |
| 结构系 | 信息怎么切块 | 主要由网格、栏数、卡片/格子、间距与密度决定 | Bento Grid、卡片式、分栏式 |

### 4.2 主归属与次归属规则

**主归属判定顺序（从上到下，先命中先定）：**

1. 是否绑定某平台，并规定组件、动效、无障碍、布局的整套规则？命中 → **平台系**。
2. 是否只规定表面材质与光学行为？命中 → **材质系**。
3. 是否只规定信息切块与排布？命中 → **结构系**。
4. 其余 → **流派系**。

**次归属规则：**

- 主归属只能 1 个；次归属最多 2 个，写在「家族归属」单元格的括号里，例如「材质系（次：平台系）」。
- 次归属不参与左栏一级筛选，只参与「相近风格」推荐。
- 判定口诀：**删掉哪个家族属性，它就不再是它**，那个就是主归属。

**跨家族示例：**

| 条目 | 主归属 | 次归属 | 判定理由 |
|---|---|---|---|
| 液态玻璃 | 材质系 | 平台系 | 表面光学行为是识别核心；但它是 Apple 平台规范的一部分 |
| Material 3 | 平台系 | 流派系（扁平） | 它规定整套组件与行为；扁平只是其视觉 DNA |
| Apple HIG | 平台系 | 材质系（Liquid Glass） | 平台规则优先；Liquid Glass 是其当前材质语言 |
| Bento Grid | 结构系 | 流派系 | 识别核心是格子切块；「苹果味」只是常见搭配 |
| 编辑式 | 流派系 | 结构系（分栏） | 识别核心是杂志式视觉语言；栏 grid 是常用结构 |

### 4.3 父子 / 近亲 / 别名怎么表达

| 关系 | 字段 | 语义 | 例子 |
|---|---|---|---|
| 演进 | `parent_id` + `relation=evolves_from` | 后者由前者演进，保留可识别的表面特征 | 玻璃拟态 → 液态玻璃 |
| 派生 | `parent_id` + `relation=derived_from` | 后者是前者的新解 | 拟物化 → 新拟态 |
| 同族近亲 | `kin_group` | 不是父子，但共享同一构造逻辑 | 新拟态 ↔ 黏土拟态（`soft-3d`） |
| 别名 | `aliases[]` | 同一物的不同叫法，不单独建案例 | 玻璃拟态 = 毛玻璃 / 磨砂玻璃；新拟态 = Soft UI |
| 组合 | `combines[]` | 一个条目由多个家族特征组合 | Bento + 玻璃拟态；编辑式 + 卡片 |

**硬规则：**

- 别名不单独占一条案例，只做检索重定向。
- 父子条目各自保留自己的边界与参数；子条目只记录相对父条的 `token_overrides`，不复制全量 token。
- 同族近亲用 `kin_group` 互链，不互相设为父子，避免出现环。
- 跨家族条目主归属唯一；次归属只做推荐，不做筛选。

### 4.4 预览参数集与家族的对应

**通用参数集（每条风格必须能给出一套，缺失用中性默认并标记 `preview_confidence`）：**

| 参数组 | 字段 | 说明 |
|---|---|---|
| 画布 | `bg.base`、`bg.surface`、`surface.opacity`、`blur`、`texture` | 背景与表面；材质系重点 |
| 色彩 | `color.primary`、`color.secondary`、`color.accent`、`color.semantic` | 主色、辅色、强调色、语义色 |
| 深度 | `shadow.outer`、`shadow.inner`、`highlight`、`border` | 外阴影、内阴影、高光、描边 |
| 形状 | `radius.scale`、`stroke.width` | 圆角刻度、描边宽度 |
| 字体 | `type.family`、`type.scale`、`type.weight` | 字体家族、字阶、字重 |
| 布局 | `grid.columns`、`grid.gap`、`density` | 栏数、间距、密度；结构系重点 |
| 主题 | `theme.light`、`theme.dark`、`theme.system`、`theme.brand` | 两套 token 必须齐备 |
| 动效提示 | `motion.signature` | 预览用的时长/缓动签名，不替代动效域 |

**家族到参数的映射：**

| 家族 | 参数重点 | 必填项 |
|---|---|---|
| 材质系 | 透明度、模糊、纹理、内外阴影、边缘高光、圆角 | `surface.opacity`、`blur`、`shadow.outer`、`shadow.inner`、`highlight`、`border` |
| 流派系 | 色彩饱和度、字体、形状纪律、装饰程度 | `color.*`、`type.*`、`radius.scale`、`texture` |
| 平台系 | 完整 token 集 + 组件默认值 + 动效签名 | 全部 8 组 |
| 结构系 | 网格、栏数、卡片/格子、间距、密度 | `grid.columns`、`grid.gap`、`density`、`radius.scale` |

**主题与家族的关系：**

- 主题不是第五个家族，而是所有家族共用的 token 维度。
- 每条风格必须提供 `theme.light` 与 `theme.dark` 两套；平台系可直接映射官方 token，材质/流派/结构系需给出推导值。
- 品牌主题只替换 `color.primary/secondary/accent`，不得改结构参数。
- 跟随系统用 `theme.system=true` 表达，不复制第三条主题。

| 加载动效 | Loading Animation | 动效 | 加载 | 收等待中的循环/进度动画；不收结果确认 | 循环、确定性、时长 | `loop`、`progress`、`reduce-motion` 降级 |
| 减弱动效 | Reduced Motion | 动效 | 可及性 | 收 `prefers-reduced-motion` 降级；不收普通动效 | 降级策略、替代 | 动画关闭或仅透明度 |

### 5.5 反馈

| 名称 | 英文/别名 | 类型 | 家族归属 | 一句话边界 | 形态要点 | 可预览参数 |
|---|---|---|---|---|---|---|
| 交互状态 | Interaction States | 反馈 | 状态 | 收 hover/focus/pressed/disabled/selected 的视觉与行为；不收页面级状态 | 状态层级、对比、焦点环 | `state layer`、`focus ring` 2px、150ms |
| 表单校验 | Validation | 反馈 | 校验 | 收何时校验、错误定位、错误摘要；不收纯文案、控件外观 | 触发时机、位置、汇总 | `inline error`、`aria-invalid`、聚焦首个错误 |
| 提交结果 | Submit Result | 反馈 | 结果 | 收成功/失败的即时反馈与下一步；不收加载中 | 结果类型、呈现、恢复 | `toast/inline/banner`、`retry` |
| 确认与撤销 | Confirm / Undo | 反馈 | 安全 | 收危险操作确认与可撤销；不收普通成功提示 | 阻断、倒计时、撤销入口 | `dialog`、`undo` 5–10s |
| 加载与等待 | Loading & Waiting | 反馈 | 状态 | 收 loading/skeleton/optimistic；不收空态、错误 | 时长阈值、占位、可取消 | 0–1s spinner、>1s skeleton、optimistic |
| 空状态触发 | Empty State | 反馈 | 状态 | 收无数据/无结果/无权限的出现时机与下一步；不收错误、加载 | 原因、行动、插图 | `empty illustration`、`cta`、`tone` |
| 错误状态 | Error State | 反馈 | 状态 | 收可恢复错误的原因/重试/降级；不收空数据 | 错误码、重试、离线 | `inline/banner`、`retry`、离线缓存 |
| 通知 | Notification | 反馈 | 通知 | 收 in-app 与 push 的时机/优先级/频控；不收权限请求 | 渠道、优先级、频控 | `toast/banner/push`、`priority` |
| 权限请求 | Permission Request | 反馈 | 系统 | 收系统权限的前置解释/时机/拒绝后路径；不收设置页 | 时机、文案、降级 | `pre-prompt`、`system dialog`、`fallback` |

## 6. Vibe Coding 词典专项

### 6.1 选源与甄别

| 来源 | 规模 | 采用情况 | 说明 |
|---|---|---|---|
| [World of Vibe Coding Glossary](https://worldofvibecoding.com/glossary?category=all&letter=all) | 63 条 / 12 个 territory | 主用 | 有 Design 分类，词条稳定，含 Bento、Glassmorphism 等界面词 |
| [vibecoding.rest Dictionary](https://vibecoding.rest/dictionary/) | 约 25 条 | 辅用 | 以 agent / context / MCP 等工程词为主，界面词极少 |
| [CodingWithVibe Glossary](https://codingwithvibe.com/vibe-coding-glossary-of-terms/) | 200+ 条 | 抽样 | 大量 ML 研究词，界面相关密度低 |
| [Blink Vibe Coding Glossary](https://blink.new/blog/vibe-coding-glossary) | 40 条 | 剔除 | 明显的产品导流与营销词，定义偏销售话术 |

**剔除标准：**

1. 没有稳定定义，只有口号或产品名（如 “AI app builder”“zero-config deployment”）。
2. 纯 ML 研究/训练词，与界面设计无关（如 AdaGrad、Ablation、Activation Functions）。
3. 同一概念的不同叫法不合并会重复计数（如 Vibecoding / Vibe Coding），保留一个 canonical，其余进别名。
4. 只在单一厂商营销页出现，且不能落到形态参数（如 “System Director”“Vibe Debt”）。
5. 与现有域无法形成「收什么/不收什么」边界的，先放候选标签，不升域。

### 6.3 对不上现有 4 域的候选

| 候选 | 为什么现有 4 域装不下 | 建议 |
|---|---|---|
| Generative UI | 它不是风格、不是组件、不是动效，也不是反馈；它是「界面由 AI 实时生成」的生产方式，会同时影响四域 | 先做跨域标签；出现稳定形态参数后再评估是否升域 |
| Design System | 它是元概念，横跨风格、组件、内容、可及性 | `design-system` 标签；不升域 |
| Thumb Zone | 它答的是「控件放哪里」，组件域只管控件本身，风格域不管人体工学 | 归新增「布局与结构」域 |
| Design Token | 它是风格与主题的实现载体，不是风格本身 | `design-token` 标签 |
| Progressive Disclosure | 它同时是信息架构策略和交互机制 | 标签，归结构/反馈 |
| Affordance | 它是跨域的设计原则，不是可预览的条目 | 标签，放「可及性/可用性」 |
| AI app builder / Prompt-to-UI | 是工具与工作流，不是界面知识 | 剔除，不入库 |
| Vibe Debt / System Director | 营销化或角色化概念，无稳定形态定义 | 剔除 |

### 6.4 结论

vibecoding 词典的**真实价值不在词量，而在用词校准**：它确认了 Bento、Glassmorphism、Neobrutalism、Tactile、Command Menu、Thumb Zone、Generative UI 这些词确实在实际对话中出现。但它对「域模型」的直接贡献有限：63 条里只有约 8 条能落到界面知识，多数是 agent / context / tooling 词。因此：

- 词典词条只用于**补充别名与标签**，不用于扩张一级域。
- 唯一值得观察的新概念是 **Generative UI**，但当前证据不足以独立成域。
- 词典中营销化条目一律剔除，避免把「做 App 的知识库」变成「AI 工具广告墙」。
