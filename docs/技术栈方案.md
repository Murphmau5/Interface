### 1.2 九条关键结论

1. **Tauri 2 稳定可用，但「Windows 7 支持」是文档与现实的冲突点**：WebView2 自 109 之后不再支持 Win7/8，项目应把最低系统定在 **Windows 10 1803+（推荐 22H2）**，不对外承诺 Win7。
2. **安装包体积不要按「Tauri 一定几 MB」来承诺**：空壳社区实测 NSIS 约 3.9–6MB、MSI 约 5–8MB；本项目含媒体解码与图像处理后，合理预期 **20–40MB**（**未验证**，必须在 Phase 1 实测）。离线安装版另加约 127MB WebView2。
3. **数据库建议从 SQLx 改为 rusqlite + bundled + 自写迁移器**：单进程、低并发、单主表 + JSON payload 的模型下，编译期 SQL 校验收益有限，而编译时间、二进制体积、内存库测试成本更高。若团队坚持异步与迁移工具链，保持 SQLx 亦可，需接受代价。
4. **素材用「内容寻址对象库 + 关联表」，不用 `assets/<caseId>/` 直接堆文件**：与宪法 §6.2 有差异，需修订。环状去重、软删除、跨案例复用都更干净。
5. **预览安全最关键的发现：Tauri 在 Windows 会把自定义协议页判为「local」**（`http(s)://<scheme>.localhost`），capability 默认可达；因此 `iframe sandbox` **绝不能带 `allow-same-origin`**，且不能把 sandbox 当作唯一防线，必须叠加「会话 token + 协议处理器白名单 + 子文档 CSP 响应头 + postMessage 校验」。
6. **Playwright 不建议塞进安装包**：V1 只做静态抓取 + 用户截图导入；Phase 6 优先「系统 Edge + CDP」或 `playwright-core` + `channel: 'msedge'`，Node SEA sidecar（约 100MB+）仅作兜底。
7. **结构化输出的硬门禁必须放在 Rust 侧**（serde + 业务规则 + schemars 生成 JSON Schema）；Zod 作为前端 IPC/导入导出的第二道校验。这与宪法「AI 输出必须通过 Zod 校验后才允许落库」的字面要求冲突，需要修订措辞。
8. **凭据库不是安全边界**：Windows Credential Manager 同一用户下任意进程可静默读取；它只解决「不落库、不落日志」，不解决本机恶意软件。`CRED_MAX_CREDENTIAL_BLOB_SIZE = 2560` 字节（不是常见的 5120 误传）。
9. **应用外壳不引入 GSAP**，GSAP 仅存在于预览运行时；外壳动画以 CSS 为主、Motion 只处理需要编排/中断/弹簧的场景。React Compiler 在 V1 不开启。

### 1.3 必须在 Phase 1 拍板的三件事

| # | 决策 | 影响 | 不拍板的后果 |
|---|---|---|---|
| P1 | WebView2 分发形式（在线 bootstrapper / offlineInstaller / fixedRuntime） | 安装包 +0 / +127MB / +180MB | 无网机器装不上，或包体失控 |
| P2 | 数据库层 rusqlite 还是 SQLx | 编译时间、二进制体积、迁移代码量 | 中途换层导致仓储重写 |

## 3. 逐项方案

### 3.1 Tauri 2 现状与 Windows 支持

**【结论】**

- 锁 `tauri 2.12.5`、`@tauri-apps/api 2.12.4`、`@tauri-apps/cli 2.12.4`。Tauri 2 于 2024-10-02 GA；`tauri 3.0.0-alpha.6` 已存在但未 GA，**V1 不采用**。`[已验证]`
- 最低系统：**Windows 10 1803+**（WebView2 运行时的最低要求），推荐 22H2 与 Win11。官方 prerequisites 写「Windows 7 and later」，但 WebView2 对 Win7/8 的支持停在 109 且 2023-01 后不再更新——这是**官方文档之间的冲突**，本项目按「不承诺 Win7/8」处理。`[已验证：冲突已标注]`
- WebView2 依赖形式（`bundle.windows.webviewInstallMode`）：`downloadBootstrapper`（默认，**需联网**）、`embedBootstrapper`（+约 1.8MB，仍需联网）、`offlineInstaller`（+约 127MB，离线可用）、`fixedRuntime`（+约 180MB，锁版本）、`skip`。`[已验证]`
- 安装包体积：**官方只给 WebView2 附加体积，不给空壳应用体积**。社区实测空壳 NSIS 约 3.9–6MB、MSI 约 5–8MB；本项目预估 20–40MB。`[未验证：社区数据 + 估算]`
- 签名：不签名仍能运行，但浏览器下载触发 SmartScreen；OV/EV 均需累积信誉，EV 自 2024 起不再「即时免拦截」。配置字段为 `bundle.windows.certificateThumbprint`、`digestAlgorithm`、`timestampUrl`、`signCommand`（`%1` 占位）。`[已验证]`
- 代码签名成本（公开价，仅供预算参考）：Azure Artifact Signing Basic $9.99/月（5000 次），Premium $99.99/月；OV 约 $219–536/年；EV 约 $829/年；2023-06 之后 OV/EV 需硬件令牌/HSM。`[已验证：公开报价，实际以供应商为准]`

**【备选与取舍】**

| 方案 | 优点 | 代价 |
|---|---|---|
| 在线 bootstrapper（默认） | 包体最小 | 无网机器装不上；首次启动可能弹 WebView2 安装 |
| offlineInstaller | 内网/离线可装 | +127MB，更新 WebView2 需重发安装包 |
| fixedRuntime | 版本可控、行为稳定 | +180MB，且需自行跟进安全更新 |
| 不签名 | 零成本 | SmartScreen 拦截、企业分发受阻、杀软误报概率上升 |

**建议**：主安装包用 `downloadBootstrapper`；同时产出一个 `offlineInstaller` 变体供内网分发；`fixedRuntime` 只在「客户环境必须锁版本」时启用。签名在 V1 至少做到「有可选项、工程预留 `signCommand`」，正式对外分发前必须签。

**【风险】**

- Win7/8 用户安装后 WebView2 停更，安全与兼容双重风险。
- 离线场景下的首次安装失败会被误判为「应用坏了」。
- 未签名版本在企业环境被 AppLocker / Smart App Control 拦截（**未验证**，需目标客户环境实测）。

**【验证方式】**

1. Phase 1 建空壳工程，用 CI 产出 NSIS + MSI，记录真实体积。
2. 在干净 Win10 1809 / 22H2 / Win11 三台虚拟机（无 WebView2、断网）各装一次，记录失败模式与提示文案。
3. 打开 Windows 事件查看器与 Defender 日志，确认无误报后再决定是否采购证书。

### 3.2 数据库：访问层、迁移、软删除与历史

**【结论】**

- SQLite 本体 **3.53.4**；开库参数建议 `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON`。WAL 下 `NORMAL` 不会损坏库，但断电可能丢最近事务——对「设计知识库」可接受。`[已验证]`
- 访问层**建议 rusqlite 0.41.1（feature `bundled`）+ tokio-rusqlite 0.8.0 + 自写迁移器**。`bundled` 由 `libsqlite3-sys` 编入 SQLite 源码，FTS5/JSON1 默认开启，免系统依赖。`[已验证]`
- 备选 SQLx 0.9.0（`sqlite` + `runtime-tokio` + `macros` + `migrate`）：`query!` 编译期校验在 0.9 起「离线模式始终启用」，需 `DATABASE_URL` 或 `.sqlx` 目录（`cargo sqlx prepare`）。`sqlx::migrate!` 使用 `_sqlx_migrations(version, description, installed_on, success, checksum, execution_time)`；SQLite 下迁移锁是空实现，**无跨进程迁移锁**。`[已验证]`
- `tauri-plugin-sql 2.6.0` 底层仍是 sqlx，默认只给 `allow-close/load/select`，`execute` 需显式授权。它把 SQL 暴露给前端，与「命令层不写 SQL、仓储统一校验」的架构直接冲突，**不采用**。`[已验证：权限默认值；「官方建议仅简单场景」为未验证]`

**【五维对比】**

| 维度 | rusqlite 0.41.1 | sqlx 0.9.0 | tauri-plugin-sql 2.6.0 |
|---|---|---|---|
| 编译时间 | 快（仅 C 编译） | 慢（依赖 + 过程宏） | 最慢（含 sqlx + 前端包） |
| 二进制体积 | 小 | 大 | 大 |
| 迁移体验 | 自写（约 50–100 行） | 内建事务 + checksum | 同 sqlx，但迁移在 Rust 侧 |
| 异步一致性 | 单线程串行（恰好匹配 SQLite 写模型） | 原生 async（仍受 SQLite 单写者限制） | 原生 async |
| 可测试性 | 内存库直接测，无编译期校验 | 强类型，但需 DATABASE_URL/.sqlx | 受 IPC/权限层干扰 |

**为什么选 rusqlite**：本项目是单进程、单用户、低并发，SQLite 本身只有一个写者；异步化带来的真实收益很小，反而引入「在 async 上下文里阻塞」的陷阱。编译期 SQL 校验对 `payload_json` 这类 JSON 字段几乎无效。代价是迁移器要自己写，但工作量固定且可控。

**【迁移方案（落地形态）】**

```
src-tauri/migrations/
  0001_init.sql
  0002_add_fts.sql
  0003_add_case_history.sql
```

- 用 `include_str!` 编译期内嵌，不依赖运行时目录。
- 版本表：

```sql
CREATE TABLE schema_migrations (
  version     INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  checksum    TEXT NOT NULL,
  applied_at  TEXT NOT NULL
);
```

- 每条迁移在**单个事务**内执行 SQL + 写入版本行；失败整体回滚。
- 启动守卫（关键）：
  1. 若 `max(version) > 应用内置最高版本`（用户回滚到旧客户端）→ **拒绝打开业务库**，提示「数据库来自更新版本」，提供「备份后以只读打开」或「退出」。
  2. 执行任何待应用迁移前，把 `db` / `-wal` / `-shm` 复制到 `backups/<appVersion>-<timestamp>/`。
  3. `PRAGMA user_version` 冗余存一份 schema 版本，作为廉价自检。
- 只写前向迁移，**不写 down**；回滚靠备份目录。
- 进程内用 `SingleInstance` 语义（Tauri 单实例）保证不会有两个进程同时迁移。

**【软删除】**

- 列 `deleted_at TEXT NULL`；所有仓储查询统一带 `deleted_at IS NULL`（在仓储层集中拼装，禁止散落）。
- 部分唯一索引（SQLite 原生支持）：

```sql
CREATE UNIQUE INDEX ux_cases_live ON cases(kind, slug) WHERE deleted_at IS NULL;
```

- 恢复 = 把 `deleted_at` 置空；彻底删除 = 显式「清空回收站」动作，且必须先备份。
- 关联表（`case_relations`、`case_assets`）在软删除时保留，真正物理清理时级联。

**【修改历史】**

- `case_history(id, case_id, version, snapshot_json, changed_fields_json, source, created_at)`。
- **写时全量快照**：内容型案例的 payload 通常 < 50KB，全量快照实现最简、可回放；diff 存储省空间但回放/合并复杂。
- 在**同一个事务**里写 `cases` 与 `case_history`；可选加触发器做审计兜底（但不作为主路径，触发器逻辑分散、难测）。
- 保留策略：每案例保留最近 N 版（建议 20）+ 手动「标记为里程碑」的版本永久保留。

**【风险】**

- 忘记过滤 `deleted_at` → 幽灵数据；靠仓储层单点封装 + 测试覆盖。
- 迁移无跨进程锁 → 依赖单实例；若未来加多窗口/多进程必须重做。
- 用户回滚客户端 → 必须靠启动守卫拦住，否则会静默读坏数据。
- 全量快照使库体积增长（含 base64 素材时尤其明显）→ 素材只存引用不存内容。

**【验证方式】**

1. `tests/migrations.rs`：空库 → 全量迁移 → 断言表/索引存在；再跑一次断言幂等。
2. 失败注入：在迁移中间制造错误，断言事务回滚且版本表无脏行。
3. 降级测试：手工把 `schema_migrations` 插入更高版本，断言启动守卫生效。
4. 软删除测试：唯一索引在软删除后可重建同 slug，恢复后冲突会被拒绝。

### 3.3 大文件素材：存储、目录、命名、缩略图、虚拟滚动

**【结论】**

- **文件系统存二进制，数据库只存元数据与引用**。数据库存 base64 会让库膨胀、备份变慢、WAL 抖动。
- 存储结构建议 **内容寻址对象库 + 关联表**：

```
<appData>/assets/objects/<sha256 前 2 位>/<sha256>.<ext>
<appData>/cache/thumbs/<sha256>_320.webp
<appData>/cache/thumbs/<sha256>_640.webp
<appData>/backups/<appVersion>-<timestamp>/
```

数据库侧：

```
assets(id, sha256 UNIQUE, mime, byte_size, width, height, duration_ms,
       original_name, created_at, thumb_state, thumb_error)
case_assets(case_id, asset_id, role, sort_order)
```

- 文件名**永不用用户原名**（原名只进库，用于展示与导出）；扩展名由 MIME 白名单映射，不用用户输入。
- 去重键是 `sha256`（`sha2 0.11.1`）；大小写统一小写规范化，避免 NTFS 不敏感造成同名冲突。
- 原子写：同目录 `*.tmp` → `rename`；**Windows 上 `rename` 不能覆盖已存在文件**，需先删或使用 `MoveFileEx(REPLACE_EXISTING)`。
- 路径限制：`MAX_PATH=260`；禁止 `< > : " / \ | ? *`、控制字符、保留名（`CON/PRN/AUX/NUL/COM1-9/LPT1-9`）、结尾空格/点。内部采用短哈希路径即可天然规避。`[已验证]`

**【缩略图生成（Rust 侧）】**

| 类型 | 方案 | 版本 | 产物 |
|---|---|---|---|
| 位图（png/jpg/webp/avif） | `image` + `fast_image_resize` | 0.25.10 / 6.1.0 | 长边 320px WebP，质量约 72（约 12–25KB/张） |
| SVG | `resvg` / `usvg` 栅格化 | 0.49.0 | 同上 |
| GIF | `gif` 取首帧 | 0.14.2 | 首帧 WebP + 标记 `animated` |
| 视频 | `ffmpeg-sidecar` 抽首帧（可选） | 2.7.0 | 首帧 WebP；ffmpeg 二进制约 34MB（7z）/109MB（zip） |
| Lottie | 不生成静态缩略图，预览内实时渲染 | dotlottie-web 0.82.1 / lottie-web 5.13.0 | — |

- 生成流程：`assets` 落库时写 `thumb_state='pending'` → 后台任务（`spawn_blocking` + 信号量并发 2–4）→ 产物写临时文件 → rename → 更新 `thumb_state='ready'`。失败记 `thumb_error`，UI 显示占位而不是无限重试。
- 视频抽帧**默认关闭**：V1 若引入 ffmpeg-sidecar，包体 +34MB 起，且需要签名与更新；更轻的替代（预览内 `<video>` + canvas 抽帧）**未验证**性能与内存。建议 V1 视频缩略图用「首帧缓存 + 用户手动生成」的折中。

**【列表虚拟滚动与内存控制】**

- 虚拟列表 `@tanstack/react-virtual 3.14.26`：网格视图按行虚拟化，overscan 1–2 行（同时挂载约 40–80 个节点）。
- 缩略图尺寸上限：**长边 320px**；`devicePixelRatio` 上限取 **2**（高缩放下最多生成 384px 档）。
- 用 `srcset/sizes` 提供 160/320 两档，列表格 160px 时优先加载小档。
- 图片走 **asset 协议 URL**（`convertFileSrc`），**不要走 IPC base64**：base64 膨胀 33% 且需序列化复制。Windows 上 asset URL 形态是 `http://asset.localhost/<编码路径>`（macOS/Linux 为 `asset://localhost/...`）。`[已验证]`
- `img loading="lazy" decoding="async"`；`content-visibility: auto` 可选，但必须配 `contain-intrinsic-size` 防滚动跳动，**预览页内慎用**（推迟首帧）。
- 若用 `blob:` URL，必须在 `load` 后下一帧 `revokeObjectURL`，避免泄漏；优先 asset URL 而非 blob。
- 内存量级参考：2000 张 320×320 RGBA 全驻留约 800MB——所以必须虚拟化 + 离屏回收；`cache/thumbs` 磁盘 LRU 建议 300–500MB。`[已验证：算术推导]`

**【风险】**

- 内容寻址存储与宪法 §6.2 的 `assets/<caseId>/` 不一致（见第 6 章差异清单）。
- 视频抽帧会显著推高包体与签名复杂度。
- Windows 长路径 / 保留名 / 大小写问题是高频坑。
- 缩略图后台任务与主线程争 IO，需限并发与低优先级。

**【验证方式】**

1. 导入 2000 张混合尺寸图片，记录：首屏时间、滚动 FPS、进程 RSS 峰值、`cache/thumbs` 体积。
2. 同一图片以不同文件名导入两次，断言只落一份对象、两条关联。
3. 断点测试：生成过程中强杀进程，断言无半成品文件（临时文件可清理）。
4. 路径穿越测试：构造 `..\`、绝对路径、保留名、超长路径的文件名导入。

### 3.4 预览隔离（最关键项）

**【核实到的关键事实】**

1. Windows 上自定义协议通过 WebView2 `AddWebResourceRequestedFilter` 暴露为 `http://<scheme>.localhost/`；Tauri 2.1.0+ 可用 `app.windows[].useHttpsScheme=true` 改为 `https://<scheme>.localhost`。`[已验证]`
2. Tauri 的「本地源」判定是独立的一套：scheme 匹配且 host 以 `.localhost` 结尾、前缀为已注册协议 → 判为 **local**，capability 默认放行。**所以 preview 协议页在 Tauri 眼里是「本地的、可信近邻」，不是天然隔离。** `[已验证：源码/测试]`
3. `withGlobalTauri` 默认 false，`window.__TAURI__` 不注入；但 `__TAURI_INTERNALS__` 由初始化脚本经 `AddScriptToExecuteOnDocumentCreated` 注入，该 API **对 iframe 同样生效** → iframe 内可能拿得到对象。`[部分验证：文档推断，未复现]`
4. 决定成败的是 **`sandbox="allow-scripts"` 且不含 `allow-same-origin`**：opaque origin → `Origin: null` → IPC 调用被拒，且拿不到父窗口对象。若同时给 `allow-same-origin`，`parent.__TAURI_INTERNALS__.invoke` 即可提权（对照 CVE-2026-82642 / CVE-2026-42184 类问题）。`[已验证]`
5. `app.security.csp` **只注入 Tauri 自己构建的 HTML**；preview 文档的真正硬约束是**协议处理器写出的 `Content-Security-Policy` 响应头**，父文档的 `frame-src` 决定能否加载，两者取交集。`[已验证]`
6. sandbox 不带同源时：`fetch` 公网**不被 sandbox 本身拦截**（受 CORS，`Origin: null`）；`localStorage`/`indexedDB` 抛 `SecurityError`；`document.cookie` 读写禁用；`postMessage` 可用但 `event.origin` 为 `null`，**不能作为身份凭据**。`[已验证：HTML Standard]`
7. 独立 `WebviewWindow` 共享同一 UserDataFolder → 同一 WebView2 浏览器进程池；协议页仍判为 local，IPC 默认可达。要真正分环境必须配独立 `dataDirectory`（Windows），而不同 `dataDirectory` 才意味着独立浏览器进程。`[已验证]`

**【结论：推荐拓扑】**

```
┌─ 主窗口 (tauri.localhost, app.security.csp 生效) ─────────────┐
│  左栏 / 中栏 / 右栏                                       │
│  ┌─ <iframe sandbox="allow-scripts"                     │
│  │        referrerpolicy="no-referrer"                   │
│  │        src="https://preview.localhost/s/<token>/<caseId>/index.html"> │
│  │  预览运行时（无同源、无 cookie、无 storage）           │
│  └───────────────────────────────────────────────────────┘
└───────────────┬───────────────────────────────────────────┘
                │ postMessage（父→子：参数/命令；子→父：ready/error/heartbeat）
        Rust 协议处理器 preview://
         · 仅接受已签发 token（一次会话一个 token，绑定 caseId）
         · 只提供会话白名单内的文件（case payload 中引用过的资源）
         · 路径规范化 + 拒绝 `..`/绝对路径/符号链接/ADS/隐藏段
         · 固定 MIME 白名单、nosniff、no-store、响应体上限
         · 写入子文档 CSP 响应头
```

- **协议处理器不直接映射用户原始目录**：会话开始时把白名单资源「物化」到 `%TEMP%/uiml-preview/<sessionId>/`（或直接从对象库按 token 读取），预览只能看见这一份拷贝。
- 打开/关闭会话走命令：`preview_session_open(caseId)` → 返回 `{ token, url }`；`preview_session_close(sessionId)` 立即删目录并吊销 token。

**【子文档 CSP（响应头，建议值）】**

```
default-src 'none';
script-src 'unsafe-inline' 'unsafe-eval' 'self';
style-src 'unsafe-inline' 'self';
img-src 'self' data: blob:;
media-src 'self' data: blob:;
font-src 'self' data: blob:;
connect-src 'none';
frame-src 'none';
child-src 'none';
worker-src 'none';
object-src 'none';
base-uri 'none';
form-action 'none';
manifest-src 'none';
```

> `'unsafe-eval'` 是用户案例常用（模板字符串/运行时编译）的现实妥协：默认关闭，若案例确需 eval，由用户在「预览安全」设置里单次授权（授权记录进库，UI 明示）。`script-src 'self'` 依赖协议处理器把脚本从同一 token 路径提供，因此仍需路径白名单。

父文档 CSP 追加：`frame-src 'self' https://preview.localhost;`（若沿用 http 形态则同时允许 `http://preview.localhost`），并保证 `img-src` 含 `http://asset.localhost` / `https://asset.localhost`。

**【postMessage 协议边界】**

```ts
// 父 → 子
type HostMsg =
  | { v: 1; type: "init";  token: string; params: unknown; theme: "dark" | "light"; viewport: { w: number; h: number; dpr: number } }
  | { v: 1; type: "params"; token: string; params: unknown }
  | { v: 1; type: "command"; token: string; action: "play" | "pause" | "replay" | "loop" | "speed"; value?: number };

// 子 → 父
type RuntimeMsg =
  | { v: 1; type: "ready"; token: string; meta: { durationMs?: number } }
  | { v: 1; type: "error"; token: string; code: string; message: string }
  | { v: 1; type: "heartbeat"; token: string; frameCount: number };
```

父端必须校验：`event.source === iframe.contentWindow`、`token` 匹配、`v` 匹配、数值字段范围（时长 0–5000ms、距离 0–400px 等）、消息速率限流（合并到每帧最多一次）。**父端永不读 iframe DOM**，子端永不接收可执行字符串。

**【独立进程 vs iframe 取舍】**

| 方案 | 隔离强度 | 代价 | 结论 |
|---|---|---|---|
| 本窗口 iframe（推荐） | 中高（Chromium 渲染进程 + sandbox + 无同源） | 最低；可并排双主题（D-008 必需） | **V1 采用** |
| 独立 `WebviewWindow` | 中（共享 WebView2 profile，仍判 local） | 需单独 capability 与窗口管理；并排双快照成本高 | 不采用 |
| 独立 WebView2 环境（独立 dataDirectory） | 中高 | 独立浏览器进程，内存翻倍 | 仅在高危案例「隔离模式」启用 |
| 独立 Electron/Chrome 子进程 | 高 | +150MB、二次签名/更新、进程管理 | 不采用 |

**【安全边界清单（验收项）】**

1. iframe **不含** `allow-same-origin`；代码评审 + 单测断言。
2. `allow-scripts` 之外不加 `allow-forms` / `allow-popups` / `allow-top-navigation` / `allow-modals`。
3. 协议处理器只接受已签发 token；token 一次性、短生命周期（会话结束即吊销）。
4. 路径规范化后必须仍在会话目录内；拒绝 `..`、绝对路径、符号链接、NTFS ADS（`:`）、以点开头的隐藏段。
5. 只返回白名单 MIME；未知类型返回 404，不返回目录列表。
6. 每个响应带 `Content-Security-Policy`、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store`。
7. 子文档 `connect-src 'none'`；预览不得发起任何网络请求（远程素材须在导入期由 Rust 抓取落地）。
8. iframe 内 `localStorage`/`indexedDB`/`cookie` 均不可用（opaque origin），运行时必须无持久状态。
9. 主应用 capability **不给**预览源任何 `fs`/`shell`/`http` 权限；仅主窗口 label 拥有应用权限。
10. 预览心跳超时（3s 无 heartbeat 或无 `ready`）→ 强制销毁 iframe 并报错，防止死循环卡主界面。
11. 预览会话结束、切换案例、窗口关闭都必须删临时目录。
12. 生产构建**绝不**暴露 CDP 调试端口（`--remote-debugging-port` 只允许开发模式）。

**【风险】**

- 「协议页被判 local」这一层认知错误会让整个方案失效——必须把 sandbox 当**第二道**防线而非唯一防线。
- 漏写子文档 CSP 响应头 = 预览可任意联网。
- `'unsafe-eval'` 授权若做成全局开关，等于给所有导入案例放行。
- Chromium 0-day 不在本方案防护范围内；只能靠及时升级 Tauri/WebView2。
- 同浏览器进程池意味着恶意案例仍可能吃满主界面 CPU/GPU；需要心跳看门狗与限帧。

**【验证方式】**

1. 写一组「攻击样例案例」作为固定回归集：读 `file:///C:/Windows/win.ini`、`fetch('https://example.com')`、读 `parent.__TAURI_INTERNALS__`、`localStorage.setItem`、死循环 `while(true)`、`alert`/`print`、打开新窗口、提交表单。逐条断言被阻断且主界面不卡。
2. WebView2 DevTools 中确认预览文档的 `document.origin === "null"`、`window.__TAURI_INTERNALS__` 调用抛出。
3. 用 `netstat` / 抓包确认预览期间无非预期外联。
4. 心跳看门狗：构造死循环案例，断言 3 秒内被回收且可继续切下一个案例。

### 3.5 Playwright 落地

**【结论】**

- **V1 不做浏览器自动化**：只做 Rust 侧静态抓取（`reqwest 0.13.5` + HTML 解析）与用户截图/录屏导入。理由：包体、签名、更新、合规成本都高，而 V1 的核心价值在本地知识库与预览。
- Phase 6 动态抓取三条路线，优先级如下：

| 路线 | 体积成本 | 复杂度 | 说明 |
|---|---|---|---|
| 系统 Edge headless + Rust CDP 客户端 | 约 0（复用已装 Edge） | 中高（自实现 CDP 子集） | **首选**；需原型验证 `msedge.exe --headless=new --remote-debugging-port=0` 的可行性与截图质量。`[未验证]` |
| `playwright-core` + `channel: 'msedge'`（sidecar） | `playwright-core` 解包约 10.3–12.7MB + Node 运行时 | 中 | 不下载 Chromium；需打包 Node |
| 完整 Playwright + Chromium | Chromium 约 160–170MB 下载、解压数百 MB；`chromium-headless-shell` 约 100–110MB | 低（生态成熟） | **不采用** |

- Node 运行时打包体积（参考量级）：Node SEA ≈ `node.exe`（win-x64 官方约 100MB）；`pkg` 原仓库已归档，维护分支为 `@yao-pkg/pkg`；`bun build --compile` 约 50–100MB；`deno compile` 约 70MB。`[已验证：官方/文档量级]`
- **不要**在生产中用 WebView2 开调试端口抓取：会污染主会话，且本机任意进程可接管。开发模式可用于调试预览。
- Tauri sidecar 配置：`bundle.externalBin`，文件名必须是 `<name>-<target-triple>[.exe]`，Windows 为 `binaries/<name>-x86_64-pc-windows-msvc.exe`。`[已验证]`

**【备选与取舍】**

- **按需启动**：只在用户点「抓取此页」时 spawn；5s 就绪超时、30s 抓取超时、串行队列（并发 1）、完成后杀进程树并删临时 profile。绝不常驻。
- **外部进程调用**（用户自装 Playwright）不可控，不推荐给终端用户。
- **PySide/Selenium** 属于另一套技术栈，与项目 Rust 后端不一致，不采用。

**【风险】**

- 系统 Edge 版本随用户更新，抓取行为可能漂移；需固定选择器与失败兜底。
- 动态抓取天然涉及登录/验证码/付费墙，必须硬编码拒绝，不能靠提示词约束。
- sidecar 二进制需要单独签名，否则触发杀软告警。
- 抓取到的页面内容是不可信数据（宪法 §7），不得拼进系统提示词的权限指令段。

**【验证方式】**

1. Phase 6 选 10 个已知动态站点（含 3 个反爬站点）做对照：静态抓取命中率 vs Edge/CDP 命中率。
2. 记录 sidecar 冷启动时间（P50/P95）与峰值内存。
3. 断网、Edge 未安装、Edge 被策略禁用三种环境下的降级路径必须可走通。

### 3.6 AI Provider 抽象

**【结论】**

- Rust 侧定义能力 trait，配置驱动注册；**provider 元数据进库，密钥进凭据库**。

```rust
#[async_trait::async_trait]
pub trait AiProvider: Send + Sync {
    fn descriptor(&self) -> &ProviderDescriptor;
    async fn chat(
        &self,
        req: ChatRequest,
        sink: &mut dyn DeltaSink,
        cancel: CancellationToken,
    ) -> Result<ChatResult, AiError>;
}
```

- `async-trait 0.1.92` 必须继续使用：Rust 1.75 的 async-fn-in-trait **不是 object-safe**，`dyn AiProvider` 无法用原生写法。`[已验证]`
- 流式：`reqwest 0.13.5` + `stream` feature → `bytes_stream`；SSE 解析**自写**（按 `data:` / `event:` / 空行分帧、`[DONE]` 结束、`id`/`retry` 忽略或记录），因为 `eventsource-stream 0.2.3`（2022-02）与 `reqwest-eventsource 0.6.0`（2024-03）维护都偏弱。`[已验证]`
- 超时与取消：`reqwest::ClientBuilder::timeout` + `tokio::time::timeout` 双层；取消用 `tokio-util 0.7.20` 的 `CancellationToken`；流式增量通过 Tauri Channel/Event 推送，带单调 `seq`，前端断线可丢弃。
- 重试：仅对 `429/5xx/连接失败` 重试，最多 2 次，带抖动退避；**一旦已向用户吐出部分 token 就不再重试**（避免重复内容）。
- 结构化输出：
  - Rust 侧用 `schemars 1.2.3` 由 Rust 类型生成 JSON Schema，随请求发给模型（若 provider 支持 `response_format=json_schema`），响应走 `serde` 反序列化 + 业务规则校验（枚举、范围、必填、置信度规则）。
  - **AI 永远不得产出 `verified`**：在 Rust 校验层硬性降级为 `estimated`，并附 `evidence`。
  - 校验失败 → 一次修复重试 → 仍失败则拒绝并写入待审核队列（不落正式表）。
- Zod 分工：前端 Zod 用于三处——IPC DTO 边界、导入/导出文件、表单输入；**不承担落库前的唯一门禁**。

**【与宪法的冲突】**

宪法 §7 要求「AI 输出必须通过 Zod 校验后才允许落库」。在 Rust 侧无法运行 Zod（TS 运行时），若强行满足，只能让 AI 输出先回前端校验再回 Rust 落库——多一次序列化、多一条信任路径，且前端被攻破时门禁失效。**建议修订为「Rust 侧 schema + 业务规则为硬门禁，前端 Zod 为第二道与 UI 安全层」**，并保留「双 schema 一致性契约测试」（同一批 golden fixtures 分别跑 Rust 校验与 Zod 校验，结果必须一致）。

**【风险】**

- 两套 schema 漂移 → golden fixtures + CI 对比。
- SSE 各 provider 方言不同（`data:` 前缀、心跳注释行、错误帧）。
- 流式取消后仍可能计费 → 记录 usage，UI 明示。
- 结构化输出对弱模型成功率低 → 强制降级与修复策略。

**【验证方式】**

1. Mock Provider：脚本化 SSE 流（正常流、半途断流、429、超时、非法 JSON、缺字段）。全部走离线单测，不碰付费 API（宪法 §10）。
2. 契约测试：同一组 payload fixtures 在 Rust 与 TS 两侧校验结果一致。
3. 取消测试：流式进行中取消，断言连接关闭、无残留任务、无重复写入。

### 3.7 凭据存储

**【结论】**

- `keyring 4.2.0` + `windows-native-keyring-store 1.1.0`（feature `windows-native-keyring-store` 默认启用），底层是 Windows Credential Manager generic credential。`[已验证]`
- keyring 4.x 已拆为 `keyring-core` + 平台 store；4.x 有 API 断裂，需明确用 core+store 形态（`v1` feature 仅提供旧 API 兼容）。`[已验证]`
- 容量上限：`CRED_MAX_CREDENTIAL_BLOB_SIZE = 2560` 字节（UTF-16 写入约 1280 字符）。**常见的「5120」是误传。** 一般 API Key 远小于此，但若存整段 JSON 配置需分片。`[已验证]`
- **隔离级别要说清楚**：凭据按 Windows 用户账户隔离，同一用户下任意进程（含非提权）可静默读取，不弹 UAC。所以它解决的是「不落库、不落日志、不随导出包外泄」，**不解决本机恶意软件**。`[部分验证：第三方分析，非微软原文]`
- 命名约定：service = 应用标识（待 Q-01 确认），account = `provider:<providerId>` / `search:<providerId>`。

**【工程约束】**

- 只在需要时 `get_password`，读入内存后立即包装为带**脱敏 `Debug`** 的新类型（`impl Debug for Secret { write!("<redacted>") }`），禁止 `Serialize`/`Clone` 泛滥。
- 禁止：写进 `settings` 表、写进日志/panic 信息/错误 `details`、写进导出包、出现在截图与崩溃报告。
- 错误信息统一映射为 `credential_unavailable`，不回显 provider 原始错误体（可能带 key 前缀）。
- 导出流程二次扫描：`settings` 与 `providers` 表的字段白名单，不做「排除某些键」的负向过滤。
- 备选 `tauri-plugin-stronghold 2.4.0`（文件库 + 口令派生）：适合「需要口令二次保护」的场景，但引入口令初始化与恢复负担，V1 不做。DPAPI（`windows 0.62.2` 的 `CryptProtectData`）可作为「加密落盘配置」的补充，不替代凭据库。

**【风险】**

- 用户换机/重装后 key 丢失 → 设置页提供「重新输入」引导，不做静默失败。
- 企业环境凭据漫游策略可能同步凭据到域账户（**未验证**）。
- 凭据管理器条目对普通用户可见（名称层面），命名不要包含敏感语义。

**【验证方式】**

1. 设置 → 读取 → 删除 全流程；同时用 `cmdkey /list` 观察条目。
2. 故意构造 provider 报错（401/403），断言日志与 UI 中无 key 片段。
3. 导出包解压搜索 key 特征串（如 `sk-`、`Bearer`）必须为零命中。

### 3.8 性能：三栏重渲染、iframe 生命周期、动画边界

**【结论】**

- 三栏用 CSS Grid：左栏固定宽、中栏 `minmax`、右栏按需显示；分隔条拖动只写 CSS 变量（`--pane-left`），不触发 React state 更新；拖动结束才落库。
- 重渲染控制：
  - 行组件 `React.memo`，key 用稳定 `caseId`（不用数组索引）。
  - Zustand 5.1.0 切片订阅 + `useShallow`，禁止整 store 订阅。
  - TanStack Query 5.106.1：本地读 `staleTime: Infinity`、`gcTime` 合理；筛选切换用 `placeholderData: keepPreviousData`；queryKey 按筛选条件拆分，避免大对象 key。
  - **React Compiler 不开启**：需 `@vitejs/plugin-react 6.2.1` + Babel 链，Vite 8/Rolldown 下生态兼容滞后，且违规会静默跳过优化；V1 先靠手写 memo/selector 定位瓶颈，后续再评估。
- iframe 生命周期：**池化 2–4 个**，按运行时类型复用；切换案例时重置 `src` 并销毁内部定时器。双主题并排（D-008）要求至少同时 2 个活跃实例。常驻复用省首帧但会残留状态——重置必须走「新建会话 + 新 token + 重设 src」，不能只发消息。
- 动画边界（见 3.8.1）。

**【3.8.1 动画归属判定清单】**

1. 只改 `transform` / `opacity`，无需中途取消或编排 → **CSS transition/keyframes**。
2. 需要编排、可中断、弹簧、退出动画 → **Motion**。
3. 需要时间线 seek/scrub/逐帧精确控制 → **预览运行时内的 GSAP**。
4. 高频 hover/press/focus 反馈 → **CSS**，避免每帧跑 JS。
5. 滚动驱动效果 → 优先 CSS `scroll-timeline` / View Transition，降级用 Motion `useScroll`。
6. 布局变化 → FLIP + transform，禁止动画 `width/top/left`。
7. `prefers-reduced-motion` → 一律 CSS 媒体查询兜底；Motion 侧再配 `useReducedMotion` 仅用于 JS 编排。
8. 2000+ 列表项入场 → 只对可视区做，禁止全局逐项 stagger。
9. 同一元素的同一属性**只允许一个驱动源**（CSS / Motion / GSAP 三选一），避免争用 `transform`。

体积参考：`m` + `LazyMotion(domAnimation)` 约 5kb gzip 起步，功能包 +24kb；完整 `motion` 组件约 43kb；`useAnimate` mini 约 3.3kb；GSAP 核心约 +23kb gzip（仅预览侧加载，不进主包）。`[已验证：官方体积页]`

**【性能预算（建议作为验收口径，非承诺值）】**

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 列表滚动 | 60fps（长任务 < 50ms） | DevTools Performance + 真机录屏 |
| 案例切换 → 预览首帧 | < 300ms（池化复用） | 埋点 |
| 空闲内存 | < 250MB（2000 项库、无视频） | 进程 RSS |
| 主线程长任务 | 单次 < 50ms | PerformanceObserver |

**【风险】**

- 预览与主界面同浏览器进程池，恶意/低质案例会拖慢外壳（只能靠看门狗）。
- Query 缓存全量保留导致内存膨胀 → 需要分页/裁剪策略。
- 池化 iframe 状态残留 → 必须每次重建会话。

**【验证方式】**

1. 2000 条案例库压测：滚动录屏 + Performance timeline 检查长任务。
2. 连续切换 20 个案例，记录首帧时间与 RSS 曲线，检查是否单调增长。
3. 打开双主题并排，确认两实例独立、无互相污染。

### 3.9 打包、版本管理与自动更新

**【结论】**

- 打包：**NSIS 为主**（支持 per-user 安装、无需管理员、安装包更小），MSI 作为企业分发备选。产物统一进 `artifacts/builds/<version>/`（宪法 §11）。
- 版本：应用版本 semver 写入 `tauri.conf.json`；**数据库 schema 版本独立编号**（见 3.2），两者不可混用。
- 自动更新：`tauri-plugin-updater 2.14.1`；签名**强制**（`plugins.updater.pubkey` + 构建环境 `TAURI_SIGNING_PRIVATE_KEY`）；支持静态 JSON（GitHub/S3）或动态服务器（204 = 无更新）。Windows 上 `installMode`：`passive`（默认）/`basicUi`/`quiet`。`[已验证]`
- **无原生回滚**：只能通过服务器下发旧版本实现降级；而旧客户端遇到新 schema 会被启动守卫拦住 → 必须同时准备「降级安装包 + 数据备份说明」。
- 建议 V1 采取「**签名安装包 + 手动分发**」，自动更新作为可开关能力（编译 feature 或配置开关），等托管端点与密钥保管落实后再启用。

**【备选与取舍】**

| 方案 | 优点 | 代价 |
|---|---|---|
| NSIS + 在线 WebView2 | 包小、per-user | 无网环境装不上 |
| NSIS + offlineInstaller | 内网可装 | +127MB |
| MSI | 企业 GPO/Intune 友好 | 体积略大，需管理员 |
| 自研更新（下载 zip 自替换） | 完全可控 | 需自行处理签名校验、原子替换、失败回滚，风险高 |

**【风险】**

- **更新私钥丢失 = 永久断更**；私钥必须离线保管 + 双人备份。
- 未签名更新包会被 SmartScreen/杀软拦截。
- 自动更新在「用户正在编辑案例」时强制重启 → 必须做「空闲/保存后提示」。
- 服务器被劫持 + 签名未校验 = 供应链攻击；`pubkey` 必须内置且不可被配置覆盖。
- 离线用户永远拿不到更新 → 提供「检查更新」手动入口与离线包下载说明。

**【验证方式】**

1. 用 CI 产出 NSIS + MSI，记录体积、安装耗时、卸载残留。
2. 模拟更新：旧版本装 → 指向测试 JSON → 更新 → 验证数据库迁移执行、备份生成。
3. 模拟密钥错误：故意用错 pubkey 签名，断言客户端拒绝更新。
4. 断网/慢网更新中断 → 断言应用仍可用、无半更新状态。

## 10. 中文搜索方案（2026-11-08 追加）

> 追加说明：本文档定稿后，项目已由其他线程初始化（`src-tauri/` 存在，`Cargo.toml` 当前使用 `sqlx 0.8` + `uuid`）。第 3.2 章的 rusqlite 建议因此变成「与既有代码不一致」的状态，需在第 6 章差异清单之外单独确认。**本节搜索方案对 sqlx / rusqlite 两条路径同样成立**，因为 FTS5 由 bundled 的 `libsqlite3-sys` 提供，与上层访问库无关。本节内容不修改前文任何结论。

### 10.1 FTS5 与 trigram 是否可用

**【结论】**

- rusqlite 0.41.1（`bundled`）绑定 `libsqlite3-sys 0.39.0`，对应 **SQLite 3.54.0**；`libsqlite3-sys` 的 `build.rs` 在 bundled 分支显式定义 `SQLITE_ENABLE_FTS5`、`SQLITE_ENABLE_FTS3`、`SQLITE_ENABLE_JSON1`（另有 RTREE/STAT4）。**不需要额外 cargo feature 打开 FTS5**，Windows 由 `cc` 静态编入 exe，**不依赖 sqlite3.dll**（仅常规 CRT）。`[已验证：源码/README]`
- **版本冲突记录**：上一轮记录「SQLite 最新稳定 3.53.4」，而 rusqlite README 称捆绑 3.54.0。两者不可能同时为真，落地时必须实测确认。
- `trigram` 分词器自 **SQLite 3.34.0** 起可用（3.34.1 发布说明：「Enhanced FTS5 to support trigram indexes」），早期文档标为 experimental。`[已验证]`
- `sqlx 0.8` 的 `sqlite` feature 同样走 bundled `libsqlite3-sys`，FTS5 可用。`[已验证：间接]`

**【版本】**

| 名称 | 版本 | 证据 |
|---|---|---|
| rusqlite（bundled） | 0.41.1 | 已验证 |
| libsqlite3-sys | 0.39.0 | 已验证 |
| 捆绑 SQLite | 3.54.0（与 3.53.4 记录冲突） | 已验证/冲突 |
| trigram 引入版本 | SQLite 3.34.0 | 已验证 |
| contentless_delete 选项 | SQLite 3.43.0 | 已验证 |

**【备选与取舍】**

- 若坚持 `sqlx 0.8`：FTS5 同样可用，无需改数据访问层；只是迁移与查询写法不同。
- 若后续切 `rusqlite`：可省掉编译期宏与 `DATABASE_URL` 负担，但搜索实现无需改动。

**【风险】**

- 若打包环境意外链接系统 SQLite（例如启用 `sqlite-unbundled`），可能出现无 FTS5 或版本不一致；必须固定 feature 并在 CI 检查 `PRAGMA compile_options`。
- SQLite 3.54.0 与 3.53.4 的冲突说明「版本号必须运行时实测」，文档数字不能直接写进安装包信息。

**【验证方式】**

```sql
SELECT sqlite_version();
PRAGMA compile_options;  -- 期望含 ENABLE_FTS5
CREATE VIRTUAL TABLE t USING fts5(x, tokenize='trigram');
INSERT INTO t VALUES ('界面设计动效');
SELECT * FROM t WHERE t MATCH '界面设';   -- 期望命中
SELECT * FROM t WHERE t MATCH '界面';     -- 期望空（<3 字符）
```

在 Windows 干净机器上跑同一段 SQL，确认无额外 DLL 依赖（用 `dumpbin /dependents` 检查产物）。

### 10.2 trigram 对中文的实际行为

**【结论】**

- 官方原文：**由少于 3 个 Unicode 字符组成的子串不匹配任何行**。因此 2 字中文词（动效、圆角、阴影、弹窗）**必然查不到**，且**没有官方变通**。`[已验证]`
- 中文按 Unicode 字符切三元组，不依赖空格，子串匹配成立（「界面设计」查「面设」可中，但前提是查询 ≥3 字符）。`[已验证]`
- `LIKE` / `GLOB` 可走 trigram 索引，前提是模式里至少有**一段 ≥3 字符的非通配片段**；不足 3 字符或纯通配会退化为全表扫描。`[已验证]`
- **contentless 表对 `LIKE` 返回 0 行**（无法回表校验），所以「trigram + LIKE 兜底」不能建在 contentless 表上。`[已验证：论坛确认]`
- 索引体积：第三方在 18.2M 行上实测，原库 1.3GiB → 3.7GiB，**索引增量约等于文本的 1.8×**；`detail='none'` 时增量约 1.15×。另有一处概称「约 3×」，应是整库比而非索引比。**中文专项倍率未验证**。`[部分验证]`
- 可选参数 `case_sensitive 0/1`（引入版本已确认存在于文档）；`remove_diacritics` 的引入版本未验证，且**开启后会失去 LIKE/GLOB 索引优化**。`[部分验证]`

**【备选与取舍】**

| 方案 | 覆盖 | 代价 |
|---|---|---|
| trigram 单层 | ≥3 字子串、中英混合 | 2 字必失效；索引约 1.8× 文本 |
| trigram + LIKE 兜底 | 同上 + 1–2 字 | 2 字走全表扫描；几万条内毫秒级（推断） |
| trigram + unigram 短语层 | 任意 ≥2 字子串 | 索引条目≈字数，查询须插空格，实现与存储翻倍 |

**【风险】**

- **2 字中文是最高频查询**（「动效」「圆角」「阴影」），只做 trigram 会得到「搜不到」的错觉，属产品级事故。
- 中文 trigram 索引膨胀没有实测数据，万级库尚可，十万级需重新评估。
- 对 contentless 表做 LIKE 兜底会静默返回 0 行，排查成本极高。

**【验证方式】**

1. 造 200 条中文样本，逐条测 1/2/3/4/5 字查询的召回与耗时。
2. 导入 1 万条后测库文件体积，与「文本字节数 × 1.8」的推算对照。
3. 对 `detail='none'` 与 `detail='full'` 分别测 bm25 排序与体积，确认 `detail='none'` 下排序是否可用（**未验证**）。

### 10.3 jieba 分词（Rust 侧）

**【结论】**

- `jieba-rs 0.11.0`（MIT）可用；内置 `dict.txt` **5,071,843 B ≈ 5.07 MB**，crate 压缩包约 4.63MiB。
- 支持自定义词典：`Jieba::with_dict(&mut R)`、`load_dict`、`add_word`。`[已验证：API 文档]`
- 初始化耗时与常驻内存**无公开数据，未验证**；只有分词速度基准，不能代替初始化数据。
- FTS5 没有内置中文分词器；官方未给 CJK 推荐方案。常见工程做法是「jieba 分词 → 空格连接 → 写入 unicode61 FTS5」。`[部分验证：实践文章]`

**【备选与取舍】**

- 用 jieba 预分词 + `unicode61` 词级索引：索引小、可按词 AND/OR、可做词级 bm25；代价是 5MB 词典、启动初始化、分词边界错配（「界面设计」切词后查「面设」不中）。
- 不用 jieba：靠 trigram 覆盖子串，靠 LIKE 兜底短词；实现最轻，但缺少词级相关度。
- 第三方 tokenizer 扩展（`libsimple`、`lindera-sqlite`）：能直接做中文+拼音，但引入外部 SQLite 扩展，与「bundled 静态链接、无额外依赖」目标冲突，**不采用**。`[部分验证]`

**【风险】**

- 5MB 词典 + 初始化可能拖慢冷启动（未验证）。
- 分词边界与用户预期不一致，会制造「明明有却搜不到」的长尾问题。
- 自定义词典若允许用户编辑，需要版本化与失效重算。

**【验证方式】**

1. 量 `Jieba::new()` 的冷启动耗时与 RSS（目标 < 100ms、< 30MB，**目标值为推断**）。
2. 用 50 条业务词（动效、圆角、拟态、弹窗、抽屉…）对照分词结果与人工预期。
3. 自定义词典加入 10 个项目管理词，验证 `add_word` 生效且重建索引后命中。

### 10.4 拼音索引

**【结论】**

- `pinyin 0.11.0`（MIT，约 **342 KiB**，2026-01 更新，维护活跃）：`ToPinyin::to_pinyin()` 迭代，`Pinyin::plain()` 取全拼、`Pinyin::first_letter()` 取首字母。`[已验证]`
- 未找到 `pinyin-rs` / `pinyin-split` 的可用 Rust 实现；可替代的有 `ib-pinyin 0.3.1`、`az-pinyin 2026.5.10`（未验证质量）。`[部分验证]`
- 多音字按词典默认读音，**不做上下文消歧**；「重」「行」「长」等会误读。

**【备选与取舍】**

| 方案 | 实现 | 代价 |
|---|---|---|
| 额外列（推荐） | `pinyin_full`、`pinyin_initials` 两个 TEXT 列，写入时计算 | 每案例约 +50–200 字节；查询简单 |
| 虚拟生成列 | `GENERATED ALWAYS AS (...)` + 索引 | SQLite 无内置拼音函数，需注册自定义函数；与 Rust 侧逻辑重复 |
| 单独索引表 | `case_pinyin(case_id, ...)` | 多一张表与同步逻辑，收益不明显 |

- 推荐**额外列 + 并入同一个 trigram FTS 表**：全拼 ≥3 字符可走 trigram；2 字首字母（如 `dx`）仍走 LIKE 兜底（与中文 2 字同一路径）。
- 不要把拼音塞进 `cases.payload_json`：搜索列应可索引、可重建。

**【风险】**

- 多音字误读导致搜不到（如「重要」读 `zhong` 而非 `chong`）。
- 同音词召回噪声（`dongxiao` 可能命中「洞箫」类无关词），需要排序权重压制。
- 拼音列与中文列混在同一 FTS 表时，bm25 权重设置不当会让拼音结果挤掉精确中文结果。

**【验证方式】**

1. 用 20 个多音字词表测输出（重点/银行/长安/重庆/音乐）。
2. 输入 `dongxiao`、`dx`、`圆角`、`yj` 四种查询，检查召回与排序。
3. 中文精确命中必须排在拼音命中之前（用 bm25 列权重验证）。

### 10.5 综合建议：先做两层，jieba 延后

**【结论】**

**V1 只做两层：trigram 子串层 + 拼音层；2 字中文用 LIKE 兜底。jieba 分词进第三层，按需再加。**

推荐实现顺序：

| 阶段 | 内容 | 覆盖 | 理由 |
|---|---|---|---|
| P1 | `case_search` FTS5（trigram）+ 中文/拼音列 + LIKE 短词兜底 | 中文 1–∞ 字、英文子串、拼音全拼/首字母 | 一层索引解决 90% 查询；无 5MB 词典负担 |
| P2（按需） | jieba 预分词 + `unicode61` 词级索引，用于 bm25 词级排序与同义词 | 词级相关度、AND/OR 组合 | 只有在「搜得准」不满足时才加，避免过早引入分词边界问题 |
| P3（可选） | unigram 短语层，替代 LIKE 兜底 | 2 字子串走索引 | 仅当库 > 5 万条、LIKE 兜底变慢时启用 |

**2 字中文的处理（关键设计）**：

1. 查询长度 < 3 → 不走 FTS，改走 `LIKE '%xx%'`，作用在 `case_search` 的**普通表**（非 contentless）或 `cases` 的标题/标签列上。
2. 本地库目标规模是万级：20k 行的 LIKE 扫描约 1–5ms（**推断**，需实测），完全可接受。
3. 若将来超过 5 万条且 2 字查询变慢，再启用 unigram 短语层（逐字空格 + 查询也插空格），不改变 UI 与命令接口。

**表结构建议（与 10.1 的验证结果一致）**：

```sql
CREATE VIRTUAL TABLE case_search USING fts5(
  title, summary, tags, keywords,
  pinyin_full, pinyin_initials,
  tokenize = 'trigram'
);  -- rowid = cases.id

-- 写入：与 cases 同一事务
INSERT INTO case_search(rowid, title, summary, tags, keywords, pinyin_full, pinyin_initials)
VALUES (?, ?, ?, ?, ?, ?, ?);

-- 检索：≥3 字
SELECT c.* FROM case_search s JOIN cases c ON c.id = s.rowid
WHERE case_search MATCH ? AND c.deleted_at IS NULL
ORDER BY bm25(case_search, 5.0, 2.0, 2.0, 1.0, 1.5, 0.5) LIMIT 50;
```

- **不用 contentless**：会失去 LIKE 兜底。
- **不用外部内容表**：拼音列是计算列，无法从 `cases` 直接取。
- 排序权重：标题 > 标签/关键词 > 摘要 > 全拼 > 首字母。
- 软删除：FTS 表不删除，查询时 join `cases` 过滤 `deleted_at`；彻底删除时同事务删 FTS 行。

**体积推算（万级）**：每案例可检索文本约 600 字符（标题+摘要+标签+关键词）→ 文本约 6MB；trigram 索引按 1.8× 约 11MB；FTS 表自身存一份文本 6MB；拼音约 2MB。合计 **约 25MB**（**推断，未验证**）。

**【备选与取舍】**

- 全上三层（trigram + jieba + 拼音）：召回最好，但冷启动、索引体积、分词边界问题同时出现；V1 不划算。
- 只做 jieba + unicode61：2 字词表现好、索引小，但任意子串（含英文片段）覆盖差，且强依赖分词质量。
- 只做 trigram：实现最省，但 2 字中文直接失效，**不可接受**。

**【风险】**

- FTS 行与 `cases` 不同步 → 搜到已删除/已修改内容；必须同事务写入 + 重建命令兜底。
- 触发器自动同步看似省事，但拼音计算仍在 Rust 侧，触发器中无法调用 → 不用触发器。
- 批量导入 1 万条时逐条重建索引会卡；需分批 + 最后 `INSERT INTO case_search(case_search) VALUES('optimize')`。

**【验证方式】**

1. 中文 1/2/3/4 字查询召回测试（含「动效」「圆角」「毛玻璃」「弹簧动画」）。
2. 拼音查询测试（`dongxiao` / `dx` / 多音字）。
3. 写入 1 万条后测：索引体积、冷查询 P50/P95、LIKE 兜底 P95、批量导入耗时。
4. 修改/软删除案例后，断言旧关键词不再命中。

## 11. BYOK 密钥与 Provider 配置（2026-11-08 追加）

### 11.1 用户自带 Key 的存取链路

**【结论】**

- 链路固定为**单向写入、永不回读明文**：

```
设置页输入
  → Tauri command `provider_key_set(providerId, plainKey)`
  → Rust 校验格式/长度（≤ 2048 字符）
  → keyring 写入 Windows Credential Manager
  → Rust 把「已配置 + 后四位 + 写入时间」写入 providers 表（非密钥元数据）
  → 只返回 { configured, last4, updatedAt }
前端不存在任何可读取明文的 command / event / 日志出口。
```

- `keyring 4.2.0` 已拆为薄壳 + `keyring-core 1.0.0` + `windows-native-keyring-store 1.1.0`；默认 feature `v1` 提供 `Entry::new(service, user)`、`set_password`、`get_password`、`delete_credential` 并自动选平台 store。`[已验证]`
- 若直接用 `keyring-core`：必须先 `keyring_core::set_default_store(Arc<CredentialStore>)`（返回 `()`），否则 `Entry::new` 报 `NoDefaultStore`。`[已验证]`
- 容量上限 `CRED_MAX_CREDENTIAL_BLOB_SIZE = 2560` 字节（UTF-16 约 1280 字符）；常规 API Key 远低于此。`[已验证]`
- keyring 默认 target 为 `user + "." + service`；**service 或 user 里出现 `.` 会串条目**。`[已验证]`

**【备选与取舍】**

| 方案 | 优点 | 代价 |
|---|---|---|
| 仅 Credential Manager（推荐） | 系统级、不落库、可审计 | 同用户进程可读；无跨机同步 |
| 凭据 + DPAPI 加密落盘 | 可离线携带配置 | 仍不防同用户；迁移复杂 |
| Stronghold 口令库 | 需要口令才可读 | 用户负担、口令丢失即不可恢复 |

**【风险】**

- 同一 Windows 用户下任意进程可静默读取（不弹 UAC）→ 它不是本机恶意软件防线，UI 必须如实说明。
- 开发期把 key 写进 `.env` 或 `tauri.conf.json` 是最高频泄漏点；只允许运行时输入。
- `last4` 若来自前端计算，会诱导前端短暂持有明文；必须由 Rust 计算后再落库。

**【验证方式】**

1. 写入后 `cmdkey /list` 能看到条目；`get_password` 仅在 Rust 内部调用。
2. DevTools 监听所有 IPC 与事件，断言从未出现完整密钥。
3. 日志全文检索 `sk-`、`Bearer`、密钥后 8 位，必须零命中。

### 11.2 OpenAI 兼容协议覆盖多服务

**【结论】**

- 统一适配器 `openai_compatible`：`base_url` + `model` + `Authorization: Bearer <key>`；端点为 `GET /v1/models`、`POST /v1/chat/completions`。`[已验证]`
- **Ollama**：本地 `http://localhost:11434/v1/`；`/v1/models` 明确支持；SDK 要求传 api_key 但「required but ignored」，curl 示例不带 Authorization。云端 `https://ollama.com/v1` 需要真实 key。`[已验证]`
- **Azure OpenAI 不是 OpenAI 兼容**：`GET {endpoint}/openai/models?api-version=...`，鉴权头是 `api-key`。V1 若要支持，需要单独适配器或可配置的 `authMode + pathPrefix`。`[已验证]`
- 设计上把「鉴权方式」抽象成枚举，而不是在业务代码里判断 provider 名字：

```rust
enum AuthMode {
    Bearer,                  // OpenAI 兼容、云端 Ollama、多数网关
    Header { name: String },  // Azure: api-key / 其他网关自定义头
    None,                    // 本地 Ollama
}
```

- `requiresKey` 由配置声明：本地 Ollama = false；OpenAI 兼容 = true。空 Key 时**不发送 Authorization 头**，而不是发送空 `Bearer `。

**【备选与取舍】**

- 为每个厂商写独立适配器：清晰但重复，V1 只需 OpenAI 兼容 + Ollama + 可选 Azure。
- 只做一个「Bearer 兼容」适配器：覆盖大多数第三方网关与 Ollama，代价是不支持 Azure/自定义头；建议加 `AuthMode::Header` 作为低成本的扩展点。

**【风险】**

- 只转发 chat 的网关没有 `/v1/models`，会让「测试连接」误报 404（见 11.3）。
- `base_url` 允许用户填写 → 可能指向内网地址（SSRF 风险）；必须限制协议为 http/https、拒绝 URL 内嵌用户名密码，并对非本机地址做私网拦截（本地 provider 显式放行 loopback）。
- 模型名大小写/别名差异，`/v1/models` 返回列表与可用模型不一定一致。

**【验证方式】**

1. 用三个端点验证：OpenAI 官方、一个第三方兼容网关、本地 Ollama。
2. 断言空 Key 时请求头中**没有** `Authorization`。
3. 用非法 `base_url`（`file://`、`http://user:pass@host`、内网 IP）测试守卫。

### 11.3 测试连接的实现

**【结论】**

- **两段式探活**：
  1. `GET /v1/models`，超时 **5s**，用于验证 base_url 与鉴权；
  2. 若返回 404/405（网关未实现）→ 退化为一次最小 chat：`max_tokens: 1`、`stream: false`、无 tools、无上下文，超时 **25s**，校验响应含非空 `choices`。
- 不建议只做 models 列表：它无法证明「模型真的可调用」；也不建议只做 completion：部分服务按次计费且慢。两段式兼顾成本与准确。
- 401 不存在（无 Key）时不发请求，直接判定「未配置」。

**【状态码到用户提示的映射】**

| 现象 | 判定 | 用户提示（中文） |
|---|---|---|
| 401 | 密钥无效或已撤销 | 「密钥无效，请重新填写」 |
| 402 | 余额不足（DeepSeek 等） | 「账户余额不足」 |
| 403 | 地区/权限受限 | 「当前密钥没有该服务的访问权限」 |
| 404 | base_url 或模型名错误 | 「地址或模型名不正确」 |
| 405 | 网关不支持该端点 | 自动降级到最小 chat，不直接报错 |
| 429 | 限流或额度耗尽 | 「请求过于频繁或额度已用完，请稍后再试」 |
| 5xx | 服务端故障 | 「服务暂时不可用」 |
| 超时/DNS/TLS | 网络层失败 | 「无法连接，请检查网络或地址」 |

- 429 不区分限流/额度：OpenAI 文档分两种文案，但稳定的 `insufficient_quota` code **未验证**；只能结合响应体关键词做启发式判断，并保留原文到日志（脱敏）。
- 重试策略：401/402/403/404 不重试；429 与 5xx 最多手动重试一次；测试连接默认**不自动重试**，避免误判。
- **绝不把响应体原样回显**：错误 JSON 可能包含密钥前缀或账号信息。

**【风险】**

- 代理/网关改写状态码，导致映射失真。
- 超时过短会在慢网络下误报「连接失败」；25s 是折中值，需按目标用户网络调整。
- 最小 chat 仍可能计费（极少量 token），UI 需说明「测试会消耗一次最小请求」。

**【验证方式】**

1. Mock Provider 脚本化返回 401/402/403/404/429/500/超时/半截流。
2. 三个真实端点回归（不纳入常规 CI，避免付费）。
3. 断网、DNS 污染、TLS 证书错误三种网络异常各测一次。

### 11.4 无 Key 时的能力降级（Rust 单一事实源）

**【结论】**

- 能力状态只由 Rust 计算并下发，前端**不得自行推断**：

```rust
struct Capabilities {
    revision: u64,
    ai: Cap { configured: bool, reachable: bool, provider_id: Option<String>, model: Option<String>, reason: Option<ReasonCode> },
    search: Cap,
}
```

- `configured` ≠ `reachable`：前者表示「有配置且密钥存在」，后者表示「最近一次探活成功」。UI 分别展示「已配置」「已验证可用」。
- 前端启动时调 `capabilities_get`，并订阅 `capabilities://changed`；只接受 `revision` 更大的事件，避免乱序覆盖。
- **双闸门**：即使前端按钮误判为可用，所有 AI/搜索 command 在 Rust 侧仍会重新检查能力状态，直接返回结构化错误 `{ code: "capability_unavailable", message, retryable: false }`。
- 本地 Ollama：`configured = true`（无需 Key），`reachable` 由一次 2s 的 `/v1/models` 探活或 TCP 探测决定；探活失败只降级标「服务未启动」，不阻断本地库功能。

**【备选与取舍】**

- 前端推断（读本地设置）→ 会出现「前端以为能用、后端没配置」的错配，明确禁止。
- 每次调用前实时探活 → 准确但慢；采用「缓存 + 手动/定时刷新 + 失败即更新」。
- 用全局开关（如 `ai_enabled`）→ 粒度太粗，无法区分「未配置」「密钥失效」「网络不通」。

**【风险】**

- 事件乱序导致旧状态覆盖新状态 → 用 revision 单调递增。
- 设置页改了 base_url 但未重新测试 → `reachable` 保持旧值；写入配置时强制 `reachable=false` 并提示重测。
- 多窗口/多进程（V1 单窗口）暂不涉及；若未来多窗口，能力状态必须走同一 Rust 源。

**【验证方式】**

1. 四种状态矩阵：无配置 / 有配置未测 / 测试成功 / 测试失败 → UI 与按钮状态逐项对照。
2. 在设置页保存后立即调用 AI command，断言返回 `capability_unavailable` 而非 500。
3. 人为发一个旧 revision 事件，断言前端忽略。

### 11.5 导出/备份时的密钥剥离

**【结论】**

- **剥离发生在写入边界，而不是导出边界**：`providers` 表结构里**根本没有密钥列**，密钥只存在于 Credential Manager。这样任何 `SELECT *`、任何通用序列化都不可能带出密钥。`[结论]`
- 导出使用**显式 DTO 白名单**（禁止 `SELECT *`、禁止直接序列化整行）：

```rust
struct ExportedProvider { id, kind, base_url, model, requires_key, credential_ref, configured }
```

- 不导出 `last4`（虽非密钥，但属于不必要的指纹）；不导出 `credential_ref` 中的账号细节时可保留 providerId 即可。
- 导入时禁用所有密钥字段，只恢复非密钥配置；用户需重新输入 Key。
- URL 校验拒绝内嵌用户名密码；日志与 panic 钩子统一脱敏。

**【备选与取舍】**

- 依赖「导出时排除某些字段」：新增字段容易漏 → 不可靠。
- 整库加密导出：用户体验与恢复成本高，V1 不做。

**【风险】**

- 未来开发者给 `providers` 加一列 `api_key` → 结构性回退；用 schema 评审 + 导出测试守住。
- 崩溃转储（minidump）可能包含内存明文；V1 不生成 minidump，错误上报只带 code。
- 第三方日志库若开启 trace 打印请求头 → 必须禁用请求头日志。

**【验证方式】**

1. 导出包解压后全文搜索密钥特征串（`sk-`、`Bearer`、后 8 位）零命中。
2. 用 `sqlite3 .dump` 检查库文件无密钥。
3. 代码审查：搜索 `SELECT *` 与 `serialize` 在导出路径的使用。

### 11.6 搜索服务密钥的命名空间

**【结论】**

- 统一 service（应用标识，最终值待 Q-01 确认），account 采用前缀命名：

```
<service> / ai:<providerId>
<service> / search:bing
<service> / search:tavily
<service> / search:brave
<service> / search:tavily#slot2   （轮换用可选槽位）
```

- 规则：**禁止在 account 中使用 `.`**（keyring 默认 target 拼接会串条目）；禁止把密钥片段写进 account 名（`cmdkey /list` 可见）。
- `credential_ref` 存于 `providers` / `search_providers` 表，Rust 解析为 keyring account；前端只看到 `configured`。
- 多 Key 轮换：写新槽位 → 测试成功 → 切换 `active_slot` → 删除旧槽位；任何一步失败都保留旧 Key。

**【备选与取舍】**

- 每个服务独立 service：隔离更彻底，但 keyring 条目分散、清理麻烦。
- 单 service + 前缀 account（推荐）：集中管理，冲突风险靠命名规则规避。
- 把所有 Key 塞进一条 JSON：受 2560 字节限制，且一处损坏全丢，不采用。

**【风险】**

- Bing（Azure）用 `Ocp-Apim-Subscription-Key` 头、Tavily 用 Bearer/`api_key` 字段、Brave 用 `X-Subscription-Token`——各服务鉴权方式不同，必须由 adapter 的 `AuthMode` 决定（**确切头名需按各家文档逐一确认，未核实**）。
- 用户同时配置多个搜索服务时，需明确「主用 + 备用」优先级，否则结果来源不可解释。
- keyring 4.x 混用 `keyring` 与 `keyring-core` 会报 `NoDefaultStore`。

**【验证方式】**

1. 三个搜索服务各配一条 Key，`cmdkey /list` 确认条目互不覆盖。
2. 轮换流程演练：新槽位失败时旧 Key 仍可用。
3. 删除 provider 时同步删除其 keyring 条目，断言无残留。

## 12. 双作用域搜索与网页抓取（2026-11-08 追加）

### 12.1 两个作用域的产品与技术边界

**【结论】**

- 同一个输入框、**两个显式作用域**：`本地库`（默认）与 `联网`。结果**不混排**，用分段控件或标签页切换，切换时保留各自的关键词与滚动位置。
- 本地作用域走第 10 章的 FTS5 方案；联网作用域走「外部 Search Provider + 抓取管线」。
- 未配置搜索 Provider 或断网时，联网标签保持可见但禁用，并给出原因（`未配置搜索服务` / `网络不可用`），而不是隐藏。
- **联网结果一律先进候选池**，不直接写入 `cases`；用户逐条审核后才入库（对应「需要强制审核」的要求）。

**【备选与取舍】**

| 方案 | 优点 | 代价 |
|---|---|---|
| 分段控件（推荐） | 作用域清晰、结果不污染 | 多一次点击 |
| 同一列表混排 + 来源角标 | 信息密度高 | 本地/远程可信度不同，混排会误导；排序不可解释 |
| 双栏并排 | 可对照 | 三栏布局下空间不足 |

**【风险】**

- 用户误以为「联网搜不到 = 本地没有」；需要在空结果时给出交叉提示（「本地库中未找到，试试联网」）。
- 联网结果的时效性/可信度与本地库不同，UI 必须标注来源域名与抓取时间。

**【验证方式】**

1. 断网、未配置、配置但测试失败三种状态下的联网标签表现。
2. 同一关键词在两个作用域的结果互不污染（本地结果不出现候选池条目）。

### 12.2 纯 HTTP 抓取（第一层）

**【结论】**

- HTTP 客户端沿用 `reqwest 0.13.5`（默认 rustls），限制重定向、响应体上限与总超时。
- HTML 解析**推荐 `scraper 0.29.0`**：基于 `html5ever 0.40` + `selectors 0.41`，构建完整 DOM，支持 CSS 选择器，适合提取 `title`、`meta[property^=og:]`、`link[rel=stylesheet]`、`img[src|srcset]`、`video/source`。入参是 `&str`（UTF-8），**不做编码探测**。`[已验证]`
- 中文站点常见的 GBK/GB2312 必须先转码：`encoding_rs 0.8.44` 做解码/嗅探，大响应流式转码用 `encoding_rs_io 0.1.8`。`[已验证]`
- `lol_html 3.0.3` 是流式重写器，可用 `element!("css")` 回调提取，但**不能跨树查询、不能输出完整 DOM**；只适合「超大页面早期截断/改写」，不适合元数据提取。`[已验证]`
- **`selectolax-rs` 在 crates.io 不存在**：Python 版是 Lexbor + Cython，不能推定 Rust 可用；自建绑定需 MSVC 工具链。**不纳入选型**。`[已验证：检索不存在]`

**【版本与取舍】**

| 库 | 版本 | 适用 | 不适用 |
|---|---|---|---|
| scraper | 0.29.0 | 元数据提取、DOM 遍历 | 超大页面（整树内存） |
| lol_html | 3.0.3 | 流式过滤/改写/早停 | 跨节点查询 |
| encoding_rs | 0.8.44 | GBK/GB2312 解码 | — |
| selectolax-rs | 不存在 | — | — |

- 抓取字段：`title`、`og:title/description/image`、`meta description`、`canonical`、CSS 链接、图片链接（含 `srcset`）、视频/封面链接、可见文本摘要。
- **不保存完整 HTML**：只保存结构化元数据 + 链接 + 可选的本地缩略图（版权边界见第 13 章内容包策略）。

**【风险】**

- 用 `scraper` 处理 5MB 以上页面会整树驻留内存，需要先按大小截断或拒绝。
- 只读 `og:` 会对没有 OG 的站点失效，需要回退到 `<title>` + 正文首段。
- GBK 识别失败会得到乱码且难以察觉；解码后需做一次「替换字符比例」检查。

**【验证方式】**

1. 选取 20 个中文站点（含 GBK 编码站点）测字段提取率。
2. 单页 10MB 的异常页面测试内存与超时。
3. 断言不保存完整 HTML，只落元数据。

### 12.3 系统 Edge + CDP（第二层，零打包体积）

**【结论】**

- **发现 Edge**：官方默认路径 `%ProgramFiles(x86)%\Microsoft\Edge\Application\msedge.exe`（Canary 在 `%LOCALAPPDATA%\Microsoft\Edge SxS\...`）；注册表 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\msedge.exe` 被广泛使用但**微软文档未明确记载**，只能作为辅助。注意 32 位进程访问 `HKLM\SOFTWARE` 会被重定向到 `WOW6432Node`。`[已验证：默认路径；部分验证：注册表]`
- **启动参数**：

```
msedge.exe --headless=new
  --remote-debugging-port=0
  --user-data-dir=<%TEMP%/uiml-crawl/<session>>
  --no-first-run --no-default-browser-check
  --disable-extensions --disable-background-networking
  --disable-sync --mute-audio
  about:blank
```

- `--headless=new` 自 Chromium 112 起；Edge 同内核，WebDriver 文档示例即用该参数。无头模式下 JS 渲染与 `Page.captureScreenshot` 正常。企业策略 `HeadlessModeEnabled` 可禁用无头，需要探测与降级。`[已验证]`
- **端口获取**：`--remote-debugging-port=0` 时写 `<user-data-dir>\DevToolsActivePort`，首行是端口、次行是 `/devtools/browser/<guid>`；必须轮询读取（写入有延迟），不能假设 9222。`[已验证]`
- **连接**：`GET http://127.0.0.1:<port>/json/version` 取 `webSocketDebuggerUrl`；`/json/list` 需按 `type == "page"` 过滤；**`/json/new?url=` 已弃用**，改用浏览器级 WS 的 `Target.createTarget`。`[已验证]`
- **加载完成判定**：`Page.enable` → `Page.navigate` → 等 `Page.loadEventFired`，再等 `Network.loadingFinished` 且 inflight=0 静默 500–1000ms 后截图；只等 `loadEventFired` 会早于懒加载图片。`[已验证：命令存在；判定策略为工程经验]`
- **截图**：`Page.captureScreenshot`（`format: png/jpeg`、`quality`、可选 `clip`）；需要固定视口时先 `Emulation.setDeviceMetricsOverride`。`[已验证]`
- **进程回收**：优先 Job Object（`win32job 2.0.3`，父进程退出连带杀全树）；兜底 `taskkill /PID <pid> /T /F`。超时或窗口关闭都必须清理临时 profile。`[已验证]`
- **能否复用 Tauri 的 WebView2**：`WebviewWindow` **没有官方截图 API**（`[已验证]`）；若靠 CDP 必须在 `additionalBrowserArgs` 开调试端口，等于把主 WebView 暴露给本机任意进程（可读页面、执行 JS），且不同参数必须配不同 `dataDirectory`。**不采用**。`[已验证]`

**【备选与取舍】**

| 方案 | 体积 | 隔离 | 结论 |
|---|---|---|---|
| 系统 Edge + CDP（推荐） | 0（复用已装 Edge） | 独立进程 + 临时 profile | 首选 |
| 隐藏 WebView2 + CDP | 0 | 共享主 WebView profile，暴露调试端口 | 否决 |
| Playwright sidecar | 10–100MB+ | 独立进程 | 兜底（12.4） |
| 纯 HTTP | 0 | 无需浏览器 | 第一层，覆盖静态站 |

**【风险】**

- Edge 已在运行时，用默认 profile 起调试端口不生效；必须独立 `--user-data-dir`。
- 企业环境禁用无头模式或未安装 Edge（Win10 早期版本）→ 需降级到纯 HTTP。
- CDP 版本漂移：只用稳定域（Page/Network/Runtime），避免实验命令。
- 无头渲染的字体/滚动条差异会影响截图观感；需要固定视口与 `--force-device-scale-factor`。

**【验证方式】**

1. 在 Win10 22H2 与 Win11 上各跑一次「发现 → 启动 → 连 CDP → 截图 → 退出」全链路。
2. 构造懒加载图片页面，对比「只等 loadEventFired」与「网络静默 800ms」的截图差异。
3. 强杀主进程，断言 Edge 子进程不残留（任务管理器 + Job Object 验证）。
4. Edge 未安装 / 策略禁用无头两种降级路径。

### 12.4 Playwright 作为可选组件（第三层）

**【结论】**

- `externalBin` 是**构建期**打包机制，文件名必须是 `<name>-<target-triple>[.exe]`，**不支持运行时可选**。`[已验证]`
- 因此「可选组件」应放在 `appDataDir/optional/playwright/` 之类的独立目录，由应用发现与校验，不写进 `externalBin`。`[结论]`
- 发现方式：配置中手填可执行路径 → 环境变量 → `where node` + `npx playwright --version`（Node 存在时）；三种都失败则提示「未安装可选组件」。`[部分验证：CLI 探测非官方专章]`
- 仅当纯 HTTP 与 Edge/CDP 都失败时启用；默认关闭，需要用户在设置页显式开启。
- 组件加载前校验：可执行文件哈希 + 签名（minisign 或 Windows Authenticode），拒绝来源不明的二进制。

**【备选与取舍】**

- 随包分发 Playwright + Chromium：放弃（+160MB 以上，签名/更新成本高）。
- 用户自行安装 Node + Playwright：可行，但目标用户门槛高；只作为「高级组件」。
- 直接把抓取做成用户手动截图上传：零依赖，但动态页面元数据缺失。

**【风险】**

- 用户环境 Node 版本不兼容、Playwright 浏览器未下载。
- 可选组件目录被执行策略（AppLocker）拦截。
- 组件升级导致行为漂移，需要版本区间校验。

**【验证方式】**

1. 干净机器（无 Node）→ 提示文案正确、不崩溃。
2. 安装 Node + Playwright 后被发现；版本过低被拒绝。
3. 篡改组件哈希后被拒绝执行。

### 12.5 候选池与正式库的隔离存储

**【结论】**

- 新增候选池表，`cases` 不参与抓取写入：

```sql
discovery_runs(id, query, provider, started_at, finished_at, status, error_code)
discovery_candidates(
  id, run_id, source_url, canonical_url, source_host,
  title, summary, raw_meta_json, fetched_at, http_status,
  dedupe_key, status,            -- new / duplicate / rejected / approved
  approved_case_id, note
)
discovery_candidate_assets(candidate_id, url, kind, byte_size, local_path)
```

- `dedupe_key` = 规范化 URL 的 hash；可选 `simhash` 做近似标题去重（V1 可只做 URL 去重）。
- 审核动作：`candidate_approve` → 走 Zod 校验 → 写入 `cases` + 来源字段 + 关联素材 → 候选标记 `approved`。
- FTS 只索引 `cases`，候选池用简单的 `LIKE`/标题过滤，**不共享同一个搜索索引**，避免未审核内容污染本地搜索。
- 保留策略：候选默认 30 天过期，用户可手动清空。

**【备选与取舍】**

- 候选直接进 `cases` 并打「未审核」标记：省一张表，但搜索/导出/统计都要额外过滤，风险高。
- 候选存 JSON 文件：查询与去重困难。
- 独立候选表（推荐）：边界清晰，审核流可追溯。

**【风险】**

- 审核通过时字段缺失（来源页已变更）→ 必须允许用户手填并标注 `estimated`。
- 候选池无限增长 → 过期清理与容量上限（如 5 万条）。
- 重复抓取同一 URL 造成重复候选 → 唯一约束 `(run_id, canonical_url)` 或按 `dedupe_key` 去重。

**【验证方式】**

1. 抓取 → 候选 → 审核入库全链路；断言入库前 `cases` 数量不变。
2. 同一 URL 抓两次只产生一条有效候选。
3. 过期清理不影响已入库案例。

### 12.6 抓取失败与反爬的识别与降级

**【结论】**

- 建立失败分类，不把「抓不到」笼统报成「网络错误」：

| 分类 | 识别信号 | 处理 |
|---|---|---|
| `robots_disallowed` | robots.txt 禁止 | 不抓，只保存链接 |
| `blocked_auth` | 302 到登录页、401 | 保存链接 + 提示需登录 |
| `blocked_captcha` | 页面含 `captcha`、`cf-challenge`、`Just a moment`、`verify you are human` | 保存链接 + 建议手动截图 |
| `paywalled` | `subscribe to continue`、付费墙脚本标记 | 只保存公开元数据 |
| `rate_limited` | 429 + `Retry-After` | 退避后最多重试 1 次 |
| `parse_failed` | 无 title/无正文 | 保存链接 + 原始状态 |
| `network_error` | 超时/DNS/TLS/连接重置 | 重试 1 次后提示 |

- **不绕过**登录、验证码、付费墙、robots（宪法 §9）；不实现验证码识别、指纹伪装、代理池。
- 降级路径固定为：完整抓取 → 元数据抓取 → 只存链接 + 用户手动截图/录屏 → 用户手填。
- 每一条候选都必须记录 `http_status` 与失败分类，便于后续批量重试。

**【风险】**

- 站点结构变化导致误判为 `parse_failed`。
- 反爬标记误伤正常页面（如教程里出现 `captcha` 字样）。
- 重试放大对目标站点的压力；必须限流（串行 + 域名级间隔）。

**【验证方式】**

1. 固定样本集：正常页、登录墙、验证码页、付费墙、403、429、超时，各 2 例。
2. 断言所有被阻止场景都不会产生「成功入库」。
3. 域名级限流：同一域名连续抓取间隔不小于 2s。

### 12.7 单次抓取的资源上限

**【结论/建议值（经验值，未验证）】**

| 项 | 上限 | 说明 |
|---|---|---|
| HTML 大小 | 5MB | 超过即中止，只保留已读取的头部元数据 |
| 重定向 | 5 次 | 超过判 `network_error` |
| HTTP 超时 | 连接 10s / 总 15s | 纯 HTTP 层 |
| CDP 导航超时 | 30s | 单页 |
| CDP 总预算 | 60s | 含启动、导航、截图 |
| 图片下载 | 单页 ≤ 30 个，总量 ≤ 20MB | 只下载缩略图候选 |
| 视频 | 只取封面与元数据 | 不下载视频本体 |
| 截图 | ≤ 2 张（整页 + 视口） | WebP/JPEG，长边 ≤ 1600 |
| 并发 | 全局 1，域名间隔 ≥ 2s | 避免压垮目标站 |

**【风险】**

- 上限过紧会误伤正常大页面；过松会让单次抓取拖垮应用。
- 图片批量下载是最容易失控的部分，必须先统计数量再下载。

**【验证方式】**

1. 用超大页面、图片瀑布流页面、无限滚动页面各测一次。
2. 断言超限时能拿到「部分结果」而不是全失败。

## 13. 万级数据量本地性能与内容包机制（2026-11-08 追加）

### 13.1 缩略图多档预生成

**【结论】**

- 三档尺寸：`160`（网格列表）、`320`（默认/表格缩略）、`640`（详情大图）。
- 生成策略：
  - 导入时**同步生成 160 + 320**（Rust 阻塞线程池，并发 2–4），保证列表立刻可用；
  - `640` **首次进入详情页时按需生成**，避免导入阶段批量解码大图；
  - 视频封面单独走「首帧」路径（默认关闭，见 3.3）。
- 存储位置：`<appData>/cache/thumbs/<sha256>_<size>.webp`；原图在 `assets/objects/`，**缓存可重建、可清理**。
- 命名由内容哈希决定，天然支持去重与跨案例复用；不使用用户原名。
- 磁盘 LRU 上限建议 **500MB**，按最后访问时间淘汰；淘汰不影响原图。
- 数据库只记 `thumb_state`（`pending/partial/ready/failed`）与失败原因，不逐档建表；文件存在性由文件系统判断。

**【版本】**

| 组件 | 版本 |
|---|---|
| image | 0.25.10 |
| fast_image_resize | 6.1.0 |
| resvg / usvg | 0.49.0 |
| gif | 0.14.2 |

**【备选与取舍】**

| 方案 | 优点 | 代价 |
|---|---|---|
| 三档预生成（推荐） | 列表/详情都命中缓存 | 磁盘占用约 3 倍单档 |
| 只生成 320，前端缩放 | 存储最省 | 详情大图模糊；缩放耗 GPU |
| 全部按需生成 | 磁盘最省 | 首次滚动出现空窗 |

- 单张 320px WebP（q≈72）约 12–25KB；1 万条三档合计约 **400–700MB**（**推断**，需实测）；若过大，把 640 降为「仅收藏项生成」。

**【风险】**

- 批量导入时同步生成会阻塞导入流程 → 必须限并发并显示进度。
- 缓存目录被用户手动删除 → 需要可重建入口，不能报错崩溃。
- 高 DPI 屏上 160 档偏糊 → DPR 上限 2，必要时用 320 档渲染到 160 逻辑像素。

**【验证方式】**

1. 导入 1 万张混合图，记录生成总耗时、缓存体积、失败率。
2. 删除缓存目录后重启，断言自动重建且列表可用。
3. LRU 触发后磁盘稳定在 500MB 附近。

### 13.2 列表虚拟滚动（中文固定行高与变高）

**【结论】**

- 选型 `@tanstack/react-virtual 3.14.26`（headless，支持纵向/横向/网格）；`react-window 2.5.3` 作为更轻的备选（约 6kb gzip）。
- **网格视图用固定行高**：中英文混排时字体度量差异会让「自适应高度」抖动，中文标题建议 `-webkit-line-clamp: 2` + 固定卡片高度（建议 232px：缩略图 160 + 标题两行 + 元信息一行）。`[建议值]`
- **表格视图用固定行高**（建议 44–48px），不做动态测量。
- **变高只允许出现在详情/列表混排等少数场景**，使用 `measureElement` + `ResizeObserver`，并设置 `estimateSize` 初值；滚动中测量会引起跳动，必须关闭滚动锚定冲突。
- overscan 1–2 行；同时挂载节点控制在 60–100 个。
- 中文断行：使用 `word-break: normal` + `overflow-wrap: anywhere`（仅对长英文/URL 生效）；不要给中文加 `break-all`，会破坏标点避头尾。
- 切换筛选/搜索时**重置滚动位置**，避免「看起来没结果」。
- `content-visibility: auto` 只用于非虚拟化的长文区块，虚拟列表内不需要。

**【备选与取舍】**

| 方案 | 适用 | 代价 |
|---|---|---|
| 固定行高网格（推荐） | 卡片列表 | 标题超长需截断 |
| 动态测量 | 高度差异大的混排 | 滚动抖动、测量开销 |
| 分页而非虚拟滚动 | 每页 50 条 | 翻页打断浏览 |

**【风险】**

- Windows 125%/150% 缩放下行高取整导致 1px 缝隙，需要 `Math.round` 与容器 `overflow: hidden`。
- 中文字体回退（微软雅黑 vs Segoe UI）导致行高不一致 → 用显式 `line-height` 固定。
- 虚拟列表 + `IntersectionObserver` 双重懒加载会互相干扰，只保留一种。

**【验证方式】**

1. 1 万条数据下滚动 30 秒，测 FPS 与长任务。
2. 125%/150%/200% 三档缩放下检查卡片是否错位。
3. 中英混排、超长标题、无标题三种极值。

### 13.3 FTS5 在万级下的体积与延迟预期

**【结论（推断，需实测）】**

- 假设 1 万条案例，每条约 600 个可检索字符（标题 + 摘要 + 标签 + 关键词）：
  - 原文 UTF-8 约 **6MB**；
  - trigram 索引约 **11MB**（1.8×）；
  - FTS 表自身存一份文本约 **6MB**；
  - 拼音列约 **2MB**；
  - 合计 **约 25MB**，加 WAL 与页开销按 1.3× 计约 **30MB**。
- 查询延迟预期：
  - ≥3 字 trigram：**5–30ms**（P50 更低）；
  - 1–2 字 LIKE 兜底：**1–5ms**（1 万行）；
  - 拼音查询：与 trigram 同量级。
- 写入成本：单条重建索引 O(文本长度)，可忽略；**批量导入 1 万条**需分批（每批 500）+ 最后 `optimize`。
- `detail='none'` 可把索引降到约 1.15×，但 bm25 与短语行为**未验证**；V1 先用默认 `detail='full'`，再按体积决定。

**【风险】**

- 上述全部是推算；中文 trigram 的实际膨胀可能高于英文。
- LIKE 兜底在长摘要列上可能扫到 600 字符 × 1 万行，慢于预期。
- 索引优化（`optimize`）期间会短暂占用 IO。

**【验证方式】**

1. 造 1 万条真实结构数据，记录库文件体积与三类查询的 P50/P95。
2. 对比 `detail=full/none` 的体积与排序正确性。
3. 批量导入计时，确认 UI 不冻结。

### 13.4 分页与游标策略

**【结论】**

- **元数据列表用 keyset（游标）分页**，不用 `OFFSET`：

```sql
SELECT * FROM cases
WHERE deleted_at IS NULL
  AND (updated_at, id) < (?, ?)      -- 降序游标
ORDER BY updated_at DESC, id DESC
LIMIT 50;
```

- 游标编码为 base64 JSON `{ v: 1, k: "updated_at", v: "<值>", id: "<uuid>" }`，前端不解析、只回传。
- **搜索结果用 top-N + 有界 OFFSET**：FTS 按 bm25 排序，深翻页无稳定游标；建议只取前 **200–300** 条，超出提示「请细化关键词」，避免深 OFFSET。
- 计数：过滤后的 `COUNT(*)` 在万级可接受（几十毫秒）；若变慢，用缓存计数或「约 N 条」。
- 切换排序键必须换游标命名空间，不能混用。

**【备选与取舍】**

| 方案 | 优点 | 代价 |
|---|---|---|
| keyset（推荐） | 稳定、无深翻页退化 | 需要复合排序键与游标编码 |
| OFFSET 分页 | 实现简单 | 深翻页 O(n)，数据变化会跳行 |
| 全量加载 + 前端虚拟 | 交互最顺 | 内存与首屏成本高，不适合万级 |

**【风险】**

- `updated_at` 精度不足（秒级）导致同秒多条排序不稳定 → 必须带 `id` 作为第二排序键。
- 编辑案例会改变 `updated_at`，正在浏览的列表出现「条目跳到顶部」→ 需要区分「编辑时间」与「创建时间」排序口径。

**【验证方式】**

1. 1 万条数据下连续翻 20 页，测每页耗时是否恒定。
2. 翻页过程中修改一条案例，断言游标不重复、不丢条。
3. 搜索深翻页被正确限制并给出提示。

### 13.5 数据库索引设计要点

**【结论】**

- `cases`：
  - 部分唯一索引：`UNIQUE(kind, slug) WHERE deleted_at IS NULL`；
  - 列表：`(deleted_at, updated_at DESC, id DESC)`；
  - 筛选：`(deleted_at, kind, updated_at DESC)`、`(deleted_at, status, updated_at DESC)`；
- 关联：`case_tags(tag_id, case_id)` 与 `case_tags(case_id, tag_id)` 双向索引；`case_relations(from_case_id)`、`(to_case_id)`。
- 素材：`assets(sha256)` 唯一；`case_assets(case_id, sort_order)`。
- 历史：`case_history(case_id, version DESC)`。
- FTS：`case_search` 的 rowid 即 `cases.id`，不额外建索引。
- 维护：批量导入后 `ANALYZE`；应用关闭或空闲时 `PRAGMA optimize`；不要为每个筛选组合都建索引。
- 排序字段建议单独存 `title_sort`（拼音/去除符号），避免每次 `ORDER BY` 调函数。

**【风险】**

- 索引过多拖慢写入与增大库体积；万级数据下 6–8 个索引足够。
- `LIKE '%x%'` 无法用普通索引，只能靠 trigram 或接受扫描。
- `deleted_at` 放在索引首列会导致「只查未删除」的扫描效率最好，但复合顺序需按真实查询验证。

**【验证方式】**

1. `EXPLAIN QUERY PLAN` 逐条检查列表/筛选/详情查询是否走索引。
2. 导入 1 万条后测插入吞吐与库体积。
3. 删除索引对照，确认没有「建了但没用」的索引。

| 指标 | 性质 | 数值/预期 | 验证阶段 |
|---|---|---|---|
| 1 万条 FTS 索引体积 | 推断 | 约 25–30MB | Phase 2 实测 |
| ≥3 字查询延迟 | 推断 | 5–30ms | Phase 2 实测 |
| 2 字 LIKE 延迟 | 推断 | 1–5ms | Phase 2 实测 |

| 批量导入 1 万条耗时 | 待测 | 未知 | Phase 2 压测 |
| SQLite 实际版本 | 待测 | 3.54.0 或 3.53.x | Phase 1 |
| 中文 trigram 膨胀倍率 | 未验证 | 可能高于 1.8× | Phase 2 |

### 13.7 内容包（content pack）机制

**【结论】**

**需要「内容包」概念，但它是可选分发物，不是应用运行的前提。**

- 应用安装包**不带内容**，只带空 schema、内置演示与导入器；内容靠内容包或用户采集增长。
- 内容包是**独立于应用更新**的 zip + manifest，可离线导入、可增量更新、可签名校验。
- 无网络时软件必须完全可用：浏览、搜索、预览、编辑、导入本地包全部不依赖网络。

**manifest 结构（`pack.json`，V1）**：

```json
{
  "format": "uiml-pack",
  "formatVersion": 1,
  "packId": "official-core",
  "packVersion": "2026.11.1",
  "schemaVersion": 3,
  "minAppVersion": "0.1.0",
  "createdAt": "2026-11-08T00:00:00Z",
  "itemCount": 1200,
  "assetCount": 900,
  "totalBytes": 48213000,
  "items": [
    { "id": "motion-ease-out-cubic", "kind": "motion", "hash": "<sha256>", "path": "items/motion-ease-out-cubic.json" }
  ],
  "assets": [
    { "sha256": "<sha256>", "path": "assets/ab/<sha256>.webp", "mime": "image/webp", "bytes": 18342 }
  ],
  "signature": { "alg": "minisign", "keyId": "<id>", "sig": "<base64>" }
}
```

- `items/*.json` 是案例 payload（元数据 + 参数 + 自绘演示源码），逐条通过 Zod 校验。
- 素材按内容哈希存放，天然去重；增量更新按 `id + hash` 比对，**只下载新增/变更项**，不做二进制 delta（`bsdiff` 复杂度高、收益有限）。

**【版本/签名】**

| 组件 | 版本 | 用途 |
|---|---|---|
| minisign-verify | 0.3.0 | 与 `tauri-plugin-updater 2.14.1` 同一套 minisign 格式，可复用密钥体系 |
| zip | 9.2.0 | 解包；用 `ZipFile::enclosed_name()` 防 zip slip |
| ed25519-dalek | 3.0.0 | 备选签名实现（若不复用 minisign） |

- 校验顺序：zip 完整性 → manifest 解析 → **manifest 签名** → 逐文件 sha256 → schema 校验 → schemaVersion 兼容性 → 暂存目录 → 原子替换。
- 签名公钥**内置于应用**，不可被配置覆盖；私钥离线保管（与更新私钥分开或同仓管理，需明确）。
- `schemaVersion > 应用支持上限` → 拒绝导入并提示升级应用，绝不尝试猜测。

**【完整性、原子性与防穿越】**

- 解压前限制条目数（如 ≤ 50,000）与解压总字节（如 ≤ 500MB），防 zip bomb。
- 拒绝绝对路径、`..`、符号链接；先解到 `staging/`，校验通过后 `rename` 替换，旧版本保留一份供回滚。
- 内容包内的 HTML/CSS 演示**仍走第 3.4 的预览沙箱**，不因为是「官方包」就放宽。
- 内容包不包含可执行文件；素材类型白名单（webp/png/jpg/svg/gif/mp4/json）。

**【内容边界（只含元数据与自绘演示）】**

- 允许：结构化参数（时长、缓动、颜色、间距）、来源链接与出处、自绘的 SVG/CSS/Canvas 演示、自己截取的软件界面图（需自有版权或已获授权）。
- 禁止：第三方站点截图、Dribbble/Behance 原图、受版权保护的视频片段、完整网页快照。
- 每条案例带 `license` 与 `provenance` 字段；审核流程与用户采集共用同一套「强制审核」。
- 官方包发布前跑一次版权清单核对；有疑问的条目降级为「仅链接 + 参数」。

**【离线与更新策略】**

- 应用启动不检查内容包；设置页提供「检查内容更新 / 从文件导入」。
- 内容包更新失败不影响已有库；保留上一版本，失败自动回滚到旧包。
- 无网络时，所有官方内容包功能降级为本地文件导入，UI 明确提示。

**【备选与取舍】**

| 方案 | 优点 | 代价 |
|---|---|---|
| 内容包 + 签名 + 增量（推荐） | 可控、可审计、可离线 | 需要打包/签名/托管流程 |
| 应用更新时捆绑内容 | 一步到位 | 包体膨胀、内容与代码耦合 |
| 在线抓取为主，不发行内容包 | 无打包成本 | 首启空库、体验差、依赖网络 |
| 内容包不签名 | 实现简单 | 可被篡改，供应链风险 |

**【风险】**

- 签名私钥丢失 → 无法发布新包；必须与更新私钥同等保管。
- 内容包 schema 与 App 版本漂移 → 强制 `schemaVersion` + `minAppVersion`。
- 版权边界最容易越线：一旦混入第三方截图，整包合规性受质疑。
- 大包（数百 MB）首次导入耗时长，需要进度与取消。

**【验证方式】**

1. 篡改 manifest 一个字节 → 签名校验失败并拒绝。
2. 构造含 `../` 条目、超大压缩比、超量条目的恶意 zip → 全部拒绝。
3. 断网安装应用 → 空库可用；导入本地包 → 全部功能可用。
4. 旧版本应用导入新 schemaVersion 包 → 明确拒绝并提示升级。
5. 增量更新：只下载变更项，体积与全量对比。
