## 6. 必须在编码前验证的技术原型（Phase 1/3）

1. **预览协议原型**：`preview://` + sandbox + CSP 能否加载 HTML/CSS/JS/图片；失败则切 Blob 单文件方案。
2. **双实例实时渲染**：两个 iframe 同时跑同一案例，内存与帧率是否可接受；不可接受则确认静态降级策略。
3. **系统主题读取与首屏注入**：Tauri 侧读取 Windows 明暗并避免闪烁；系统强调色是否读取、是否采用。
4. **FTS 中文检索**：`unicode61` vs `trigram` 在真实中文样本上的命中与索引体积。
5. **SQLite 写入并发**：WAL + 单写队列在导入/审核并发下的表现。

## 9. 自检结论

文档层面没有未解决的**互相矛盾**；所有冲突均已落到「已修复」或「明确待确认 + 两套方案」。剩余风险集中在预览沙箱与双实例渲染两个工程问题上，必须在 Phase 3 开始前用原型验证，不允许直接按假设开发。

本次增补后新增两类必须盯住的风险：

1. **合规风险**：依赖许可与第三方素材，必须由构建期检查与发布前审计兜底，不能只靠文档承诺。
2. **交互一致性风险**：导航栈、底部条带、搜索、左栏类目四套筛选入口叠加时，必须始终只有一个类型状态，且摘要可逐项移除；否则会出现「两套筛选打架」。
